# 이사 갈 곳 찾기 (Moving Advisor)

내년 이사를 앞두고 "어디로 가야 할지" 막막한 사람을 위해, 직장 위치·예산·평형과
"무엇을 가장 중요하게 볼지"(예산/통근/학군/치안·생활편의)를 입력하면 **전국 250개 이상
시/군/구**를 점수로 정리해 추천해 주는 웹 앱 프로토타입입니다. Next.js(App Router)
기반 풀스택 앱이며, 별도 데이터베이스 없이 서버 API 라우트에서 바로 계산합니다.

## 1. 지금 무엇이 되나요 (MVP 범위)

- **지도 우선 위치 선택** (① 모드): 조건 입력보다 지도가 먼저 나옵니다. 페이지를 열면
  브라우저 위치 권한을 조용히 물어봐 "내 위치"를 파란 점으로 표시하고, 지도를 클릭해
  아무 지점이나 검색 중심점으로 고르거나(검은 다트 핀), 주요 업무지구 9곳 중 하나를 칩
  버튼으로 바로 선택할 수도 있습니다. 이 중심점 기준으로 "반경으로 찾기"(3~50km 슬라이더,
  반경 안에 몇 개 지역이 있는지 실시간 표시)와 "시/도로 찾기"(17개 시/도 중 선택) 두
  방식 중 고를 수 있고, 이렇게 좁힌 지역군 안에서만 랭킹·실거래 조회를 수행합니다(전국
  250개 이상을 매번 다 조회하지 않아 API 호출도 줄고 결과도 더 관련성 높게 좁혀집니다).
  → 자세한 배경은 11번 섹션 참고.
- **거래유형 선택(매매/전세/월세)**: 매매는 "목표 예산", 전세는 "필요 전세보증금", 월세는
  "필요 보증금(월세는 매물별로 별도 표시)"으로 입력 문구가 자동으로 바뀝니다. 월세는
  "예산을 하나의 숫자로 단순화"하는 원칙에 따라 보증금만 예산 필터 기준으로 쓰고, 월세
  금액은 매물 카드에 별도로 표시합니다.
- 목표 예산(억원) + 원하는 평형 입력 → 예산 적합도 점수 계산
- 4개 요소(예산·통근·학군·치안/생활편의) 가중치를 슬라이더로 직접 조절
- **전국 250개 이상 시/군/구**를 종합 점수순으로 정렬해 카드로 표시 (요소별 막대그래프 +
  상세 수치, 시/도명을 함께 표기해 "중구"처럼 이름이 겹치는 지역도 구분됩니다)
- **국토교통부 실거래가 API를 서비스키만 넣으면 실시간으로 연동**하도록 구현 — 매매뿐
  아니라 전월세(전세/월세) API까지 지원합니다 (키가 없으면 조사된 참고 가격으로 자동
  폴백 — 앱은 항상 정상 동작합니다. 단, 참고 가격은 현재 서울 25개 구만 조사되어 있고,
  나머지 전국 지역은 키가 없으면 예산 참고값 없이 "직접 입력" 안내만 표시됩니다 — 3번
  섹션 참고)
- **집 조건 필터**: 주택 유형(아파트/연립다세대·빌라/오피스텔), 준공 연식, 희망 방(룸)
  개수, 희망 화장실 개수를 입력하면 상위 3개 추천 지역 안에서 조건에 맞는 **실제 거래
  단지 후보**(단지명·법정동 위치·준공년도·전용면적·최근 거래가, 월세는 보증금+월세금액)를
  보여줍니다. 이 기능은 국토교통부 실거래가 API를 실시간으로 조회해야만 의미가 있어서,
  `MOLIT_SERVICE_KEY`가 없으면 자동으로 숨겨지고 안내 문구만 표시됩니다(개별 단지 정보는
  참고값으로 대체할 수 없어 조사 데이터로 흉내 내지 않습니다).
  > 아파트 유형에는 "주상복합"이 포함되어 있습니다. 아파트와 주상복합을 별도 항목으로
  > 분리하는 것은 이번 개편에서는 보류했습니다 — 국토부 아파트매매 실거래가 데이터셋이
  > 이 둘을 하나의 데이터로만 제공해서, 안정적으로 구분하려면 별도의 판별 로직(단지명
  > 패턴 매칭 등, 오분류 위험이 있음)이 필요하기 때문입니다. 필요해지면 `lib/molit.js`의
  > `HOUSE_TYPES`에 새 항목을 추가하고 판별 로직을 붙이는 방식으로 확장할 수 있습니다.
- **입력 모드 두 가지**: 화면 상단에서 전환할 수 있습니다.
  - ① 어디로 갈지 추천받기 — 위에서 설명한 기존 흐름(조건 → 전국 지역 랭킹)
  - ② 지역은 정했어요, 집만 찾을래요 — **지역을 먼저 고르면**(시/도별로 묶인 드롭다운에서
    전국 250개 이상 지역 중 선택) 그 지역·평형·주택유형·거래유형 기준으로 "필요 예산"
    구간이 자동으로 계산되어 펼쳐지고, 그 예산 범위 안에서 조건에 맞는 실제 매물이
    목록으로 나옵니다. 목록에서 매물을 클릭하면 전용면적·층·준공년도·최근 거래가(또는
    보증금/월세)·추정 방/화장실 구성 같은 상세 정보가 펼쳐지고 지도가 그 위치로
    확대됩니다.
- **"필요 예산" 자동 계산의 이상치 방지**: 실거래 표본이 5건 이상이면 단순 최소~최대가
  아니라 **10~90 백분위수**로 범위를 계산합니다. 단 하나의 극단적인 급매·신고가 거래
  때문에 범위가 비정상적으로 넓어지는 것을 막기 위함입니다(화면에 "상하위 10%를 제외한
  실제 범위"라고 표시). 표본이 2~4건으로 적으면 백분위수 계산이 오히려 왜곡될 수 있어
  실제 최소~최대를 그대로 사용합니다.
- **지도 표출**: API 키 없이 동작하는 OpenStreetMap 기반 지도(Leaflet)에 ① 모드에서는
  추천 상위 10개 지역을, ② 모드에서는 선택한 지역의 중심과 조건에 맞는 매물 위치를
  표시합니다. 개별 매물의 정확한 좌표는 공공데이터에 없어 OpenStreetMap Nominatim으로
  최선을 다해 지오코딩하고, 찾지 못하면 지역 중심 근처에 근사 위치로 표시하며 점선
  테두리로 "정확한 위치 아님"을 명시합니다.
- **매물 "다트 착지" 연출** (② 모드, ①의 위치 선택 지도에도 동일한 연출을 재사용): 새
  검색 결과가 도착하면 지도 위 매물 핀(또는 ①에서는 검색 중심점 핀)이 화살처럼 날아와
  순서대로 "파팍" 꽂히는 애니메이션이 재생됩니다. 착지 순간마다 Web Audio API로 즉석
  합성한 타격음과 기기 진동(`navigator.vibrate`, 지원 기기 한정)이 함께 나갑니다. 외부
  음원 파일은 쓰지 않으며, 후보 선택/해제처럼 결과가 바뀌지 않는 재렌더링에서는 재생되지
  않고 정적으로만 표시됩니다. 브라우저 자동재생 정책 때문에 버튼 클릭 시점에 소리가 미리
  허용됩니다.
- **"이사 갈 곳 추천받기" 클릭 애니메이션 + 서스펜스** (① 모드): 버튼을 누르는 순간 지도가
  검색 중심점으로 부드럽게 확대(flyTo)되면서 위 다트 애니메이션과 소리가 함께 재생되고,
  버튼 문구가 "위치를 확인하는 중...” → "OO 지역들을 비교하고 있어요..."로 바뀌며 최소
  약 2초 정도 뜸을 들인 뒤 결과가 나타납니다(실제 API 응답이 더 빨라도 이 시간만큼은
  기다립니다) — 결과가 너무 갑자기 튀어나오지 않고 "분석하고 있다"는 느낌을 주기 위함입니다.
- **모바일 최적화 + 지도 확대/축소**: 좁은 화면에서는 패딩·글자 크기·버튼 크기가 자동으로
  조정되고, 조건 입력 슬라이더/버튼은 터치하기 쉬운 크기로 커집니다. 지도는 마우스 휠과
  두 손가락 핀치 모두로 확대/축소할 수 있습니다(이전에는 마우스 휠 확대가 꺼져 있었습니다).
- **네이버 부동산 링크**: 매물 후보 카드마다 "네이버 부동산에서 보기" 링크가 붙습니다.
  국토부 실거래 데이터에는 정확한 주소가 없어(법정동까지만 제공) 특정 매물로 바로
  연결하는 딥링크는 만들 수 없고, 대신 법정동+단지명으로 네이버 부동산 검색 결과 페이지로
  연결합니다 — 검색 결과 목록에서 실제 매물을 직접 찾아야 합니다.
- **매물 2개 나란히 비교** (① 모드): 서로 다른 추천 지역에 있는 매물이라도 각 후보 카드의
  "비교" 체크박스로 최대 2개까지 고르면, 화면 하단에 고정된 비교함에 가격·평당가·평형·
  준공년도·층·방구성·거래월·예산 이내 여부·네이버 링크를 나란히 표로 보여줍니다. 더
  저렴/더 넓음/더 신축인 쪽에는 참고용 배지가 붙습니다(어디까지나 사실 비교이고, 무엇이
  "더 좋다"는 판단까지 대신하지는 않습니다). 3번째를 고르면 가장 먼저 고른 항목이
  자동으로 빠지고 새 항목이 들어갑니다.

## 2. 실행 방법

```bash
npm install
npm run dev
# http://localhost:3000 접속
```

프로덕션 빌드:

```bash
npm run build
npm run start
```

## 3. 데이터가 "진짜"인지 표시하는 방법

이 앱이 다루는 요소는 데이터 신뢰도가 서로 다릅니다. 사용자를 속이지 않기 위해
화면과 코드에 출처를 명시적으로 구분해 두었습니다.

| 요소 | 상태 | 설명 |
|---|---|---|
| 지역 코드/좌표(법정동코드, 위도·경도) | **실제 값(전국 250개 이상)** | 공공데이터포털 법정동코드 기준 데이터와 실제 행정구역 경계(폴리곤) 중심좌표로 계산했습니다. 시/군/구 통합 개편(예: 강원→강원특별자치도, 전북→전북특별자치도), 군위군의 대구광역시 편입(2023) 등 행정구역 변경 사항을 반영했습니다. |
| 예산/가격대 (서울 25개 구) | **실시간 연동 가능** | `MOLIT_SERVICE_KEY` 설정 시 국토교통부 실거래가 API(매매/전세/월세)를 매 요청마다 호출해 최근 거래 기준 평당가를 계산합니다. 미설정 시 `lib/districts.js`에 조사해 둔 2025년 하반기~2026년 초 참고 평당가(매매 기준)로 자동 폴백합니다. |
| 예산/가격대 (서울 외 전국 225개 지역) | **API 키 있으면 실시간, 없으면 "참고값 없음"** | 아직 참고 평당가를 조사하지 못한 지역입니다(`indexResearched: false`). `MOLIT_SERVICE_KEY`가 설정되어 있으면 이 지역들도 실시간 실거래로 예산이 계산되지만, 키가 없으면 예산 점수는 중립값(50점)으로, "필요 예산" 자동계산은 "참고값 없음 — 직접 입력해 주세요"로 정직하게 표시됩니다(가짜 숫자로 채우지 않습니다). |
| 통근시간 | **추정치** | 선택한 직장 좌표와 각 지역 중심 좌표 간 직선거리를 대중교통 평균 이동속도(약 18km/h)로 환산한 값입니다. 실제 경로/환승을 반영하지 않습니다. |
| 학군/교육, 치안/생활편의 | **참고 지수(서울 25개 구만, 0~100)** | 정확한 공공 API를 아직 연결하지 못해, 일반적으로 알려진 특성(목동·강남·서초·노원 등)을 참고해 만든 상대 지수입니다. 서울 외 지역은 아직 조사되지 않아(`indexResearched: false`) 점수 계산 시 중립값(50점)으로 대체되고, 결과 카드에는 "미조사"로 표시됩니다. |
| 실제 매물 후보(단지명/위치/준공년도/거래가) | **API 키 있을 때만 실제 데이터** | 국토교통부 실거래가 API(주택유형 3종 × 거래유형 매매/전월세)에서 받은 개별 거래 원자료입니다. 참고값으로 대체할 수 없는 정보라, 키가 없으면 후보 자체를 표시하지 않고 안내 문구만 보여줍니다. |
| 매물 후보의 방(룸)/화장실 개수 | **전용면적 기반 추정치** | 공공데이터에 방/화장실 개수 필드가 없어 `lib/roomEstimate.js`의 면적대별 관례(예: 60~85㎡→3룸·욕실2개)로 추정합니다. 실제 평면과 다를 수 있어 항상 "(추정)"이라고 표시합니다. |
| "필요 예산" 자동 계산 범위 | **API 키 있으면 실제(백분위 기반), 없으면 추정/없음** | 키가 있고 실거래 표본이 5건 이상이면 10~90 백분위수 범위(극단치 제외), 2~4건이면 실제 최소~최대를 보여줍니다. 키가 없으면 조사 참고 평당가 × 평형에 ±18~20%를 씌운 추정 범위(서울만 가능)이며, 그마저 없으면(서울 외 지역 + 키 없음) 범위 자체를 비워두고 "참고값 없음"이라고 표시합니다. |
| 매물 지도 좌표 | **최선을 다한(best-effort) 추정** | OpenStreetMap Nominatim으로 "법정동 + 단지명"을 지오코딩합니다. 실패하면 지역 중심 근처에 결정적으로 흩뿌린 근사 위치를 쓰고, 지도에 점선 테두리로 표시해 정확한 위치가 아님을 알립니다. |

결과 화면에도 각 지역 카드에 "조사 참고값"/"미조사"/"실거래가 YYYYMM 실시간" 같은 배지나
문구가 붙어 지금 보고 있는 숫자가 실시간 데이터인지, 참고값인지, 아예 조사되지 않은
값인지 항상 알 수 있습니다.

## 4. 실거래가 API 실시간 연동 켜기 (5분)

1. https://www.data.go.kr 회원가입
2. 아래 데이터셋에서 각각 **활용신청** (즉시 승인, 무료) — 최소 "아파트 매매"만 신청해도
   구 단위 가격/전체 앱은 정상 동작하며, 연립다세대·오피스텔이나 전세/월세까지 보려면
   나머지도 함께 신청하세요.
   - 국토교통부_아파트 매매 실거래자료
   - 국토교통부_아파트 전월세 자료
   - 국토교통부_연립다세대 매매 실거래자료
   - 국토교통부_연립다세대 전월세 자료
   - 국토교통부_오피스텔 매매 실거래자료
   - 국토교통부_오피스텔 전월세 자료
3. 마이페이지 > 개발계정에서 발급된 **일반 인증키(Decoding)** 복사 (보통 같은 키를
   여러 데이터셋에서 공유합니다)
4. 프로젝트 루트에 `.env.local` 파일을 만들고 아래처럼 입력

   ```
   MOLIT_SERVICE_KEY=발급받은키
   ```
5. 서버 재시작 → 화면 상단 배지가 "실거래가 실시간 연동 중"으로 바뀌고, 상위 3개 구 아래에
   "실제 매물 후보" 목록이 나타납니다.

> 참고: 공공데이터포털은 승인 후에도 API 요청 URL·응답 필드명이 데이터셋 개편에 따라
> 조금씩 바뀔 수 있습니다. **6개 데이터셋(아파트·연립다세대·오피스텔 × 매매·전월세) 전부**
> 사용자가 제공한 공공데이터포털 공식 기술문서(구/신규 API 코드 신구대조표 포함)로 실제
> 서비스 URL과 응답 필드명을 확인 완료했습니다 — 신규 API는 `dealAmount`/`excluUseAr`/
> `umdNm`/`aptNm`(또는 `offiNm`/`mhouseNm`)/`buildYear`/`deposit`/`monthlyRent` 같은
> camelCase 영문 태그만 쓰고 한글 태그는 전혀 쓰지 않습니다. 6개 API 모두 문서의 요청/응답
> 예제를 그대로 재현해서 파싱(전월세는 전세/월세 필터링까지)까지 검증했습니다. 그래도
> 국토부가 응답 스펙을 다시 바꾸는 경우를 대비해, 연동 후 매물 후보가 비어 있거나 특정
> 값이 안 보이면 브라우저 개발자도구 네트워크 탭이나 서버 로그로 실제 XML 응답을 확인해
> `TAG_CANDIDATES`에 실제 태그명을 추가해 주세요. (`fetch`를 모킹해 파싱·필터링 로직
> 자체는 이미 자동 테스트로 검증해 두었습니다 — 아래 8번 참고.)
>
> **국토부 API의 초당 요청 제한(30tps)**: 기술문서에 "초당 최대 트랜잭션 30tps"라고 명시되어
> 있습니다. 전국 250개 이상 지역을 ① 모드에서 한꺼번에 조회하면 이 한도를 쉽게 넘겨 HTTP 429
> (요청 과다) 오류가 날 수 있다는 것을 실사용자 테스트로 확인했습니다. `lib/molit.js`에 모든
> 국토부 API 요청을 초당 최대 20건으로 줄지어 보내는 공용 큐를 추가했고, 그래도 429가 오면
> 지수 백오프(0.5초→1초→2초)로 최대 3번 재시도합니다. 그래도 429가 계속되면 해당 지역만
> "국토부 실거래가 API가 HTTP 429(요청 과다) 오류를 반환했습니다"라는 메시지와 함께 안내됩니다.
>
> **키를 등록했는데도 ② 모드에서 지도/목록이 계속 비어 있다면**: 가장 흔한 원인은
> 데이터포털이 "HTTP 200 + 오류 메시지가 담긴 XML"을 돌려주는 경우입니다(서비스키가 아직
> 승인 대기 중이거나, "Encoding" 키를 잘못 넣었거나, 해당 주택유형 데이터셋을 활용신청하지
> 않은 경우 등). 이런 경우는 화면상 에러 없이 그냥 "매물 없음"으로만 보였는데, 이제는
> `lib/molit.js`가 이 오류 응답을 감지해 예외로 던지고, ② 모드 화면의 "2. 필요 예산"
> 섹션에 원인 메시지를 바로 보여줍니다(지역을 고르는 즉시 나타나므로 "매물 찾기"를 누르기
> 전에 원인을 알 수 있습니다). 이 메시지가 보이면 데이터포털 마이페이지에서 활용신청
> 승인 상태와 키 값을 다시 확인해 주세요.

## 5. 다음 단계로 발전시키려면

### 5-1. 서울 외 지역의 참고 평당가/학군·치안·생활편의 지수 조사

전국 250개 이상 지역 중 서울 25개 구만 참고 평당가와 학군/치안/생활편의 지수가 조사되어
있습니다(`lib/districts.js`의 `indexResearched: true`). 나머지 225개 지역은 이 값들이
모두 `null`이고, `MOLIT_SERVICE_KEY`가 없으면 예산/학군/치안/생활편의 점수가 모두 중립값
50점으로 계산됩니다(가짜 숫자를 만들어내지 않기 위한 의도적 설계입니다 — 3번 섹션 참고).
이 지역들도 서울처럼 실제 조사값을 채우려면 아래 공공데이터를 `lib/districts.js`의
`pricePerPyeong` / `schoolIndex` / `safetyIndex` / `amenityIndex` 자리에 채우고
`indexResearched: true`로 바꾸면 됩니다. 구조(어댑터 패턴)는 이미 `lib/molit.js`와 동일한
방식으로 확장할 수 있게 되어 있습니다.

- **학군**: 학교알리미(schoolinfo.go.kr) 공시자료, 또는 공공데이터포털
  "전국초중고등학교위치표준데이터"로 자치구별 학교 수·유형을 계산
- **치안**: 경찰청 "범죄 발생 지역별 통계"(data.go.kr) — 인구 대비 5대 범죄 발생률
- **생활편의**: 공공데이터포털 "전국 병원정보 표준데이터", "전국 도시공원정보표준데이터",
  "전국 대규모점포(대형마트) 표준데이터"를 자치구 기준으로 집계
- **통근시간 정밀화**: Kakao Mobility 길찾기 API, ODsay 대중교통 API 등으로 직선거리
  추정을 실제 경로 기반으로 교체
- **매물 좌표 정밀화**: Nominatim 대신 카카오/네이버 지도 로컬 검색 API(키 필요)로 교체하면
  지오코딩 성공률과 속도가 크게 좋아집니다. `lib/geocode.js`의 `geocodeOne` 함수만 바꾸면 됩니다.

## 7. 알려진 한계

- 전국 250개 이상 시/군/구의 위치·법정동코드는 실제 값이지만, 참고 평당가와 학군/치안/
  생활편의 지수는 아직 서울 25개 구만 조사되어 있습니다(§5-1). `MOLIT_SERVICE_KEY`가
  없으면 서울 외 지역은 예산/학군/치안/생활편의가 모두 중립값(50점)으로 계산되고, 화면에
  "미조사"/"참고값 없음"으로 정직하게 표시됩니다.
- 아파트/주상복합은 하나의 유형으로 묶여 있습니다(§5-2, 이번 개편에서 보류).
- 전월세(전세/월세) API 3종은 문서 조사만으로 구성했고 실제 서비스키로 라이브 검증은
  하지 못했습니다(§4 안내 참고). 응답이 비어 있다면 `lib/molit.js`의 `TAG_CANDIDATES`에
  실제 태그명을 추가해 주세요.
- 통근시간은 추정치이며, 실제 지하철/버스 환승을 반영하지 않습니다.
- "필요 예산" 자동 계산은 표본이 5건 이상일 때만 10~90 백분위수를 쓰고, 그보다 적으면
  실제 최소~최대를 그대로 씁니다 — 표본이 아주 적을 때(2~4건)는 여전히 극단치에 민감할
  수 있습니다.
- "실제 매물 후보"는 상위 3개 지역, 각 지역 최근 2개월 거래만 훑습니다(응답 속도와 API
  호출량을 고려한 프로토타입 범위). 필요하면 `app/api/recommend/route.js`의
  `CANDIDATE_DISTRICT_COUNT`와 `lib/candidates.js`의 `monthsBack`을 늘리세요.
- 방/화장실 개수는 전용면적 기반 추정치이며, 실제 평면과 다를 수 있습니다.
- 매물 지도 좌표는 Nominatim best-effort 지오코딩입니다. 사용 정책상 초당 1건으로 제한해
  구별로 최대 6개 단지까지만 실제 지오코딩하고, 나머지는 지역 중심 근사치로 표시합니다
  (검색 결과가 많을수록 응답이 느려집니다 — `lib/geocode.js`의 `NOMINATIM_MAX_LOOKUPS` 참고).
- 인증/회원가입, 즐겨찾기 저장 등은 아직 없습니다(단일 세션 프로토타입).

확인했습니다 (별도 테스트 러너 없이 plain Node 스크립트로 작성했습니다. 프로젝트에
포함되어 있지는 않으니, 필요하면 아래 내용을 참고해 `tests/` 폴더로 옮기고
`node --test`나 Vitest 등으로 정리하는 것을 추천합니다):

1. **`lib/roomEstimate.js`의 경계값 테스트**: 44.9/45/59.9/60/84.9/85/114.9/115㎡ 등
   구간 경계에서 방/화장실 추정이 올바르게 바뀌는지 확인
2. **XML 파싱 이중 태그 테스트**: 한글 태그(거래금액/전용면적/...)와 영문 태그
   (dealAmount/excluUseAr/...) 두 가지 응답 형식 모두에서 필드를 올바르게 뽑아내는지 확인
3. **`findCandidates` 통합 테스트**: `global.fetch`를 모킹해 실제 프로덕션 코드
   (`lib/candidates.js` → `lib/molit.js`)를 그대로 실행하며 평형 허용오차(±22%), 준공연식
   필터, 희망 방 개수 필터, 예산 초과 배지가 모두 올바르게 동작하는지 확인
4. **엔드투엔드 확인**: `npm run build` 성공, 실제 서버 기동 후 Playwright로 화면을
   캡처해 폼 입력→추천 결과→매물 후보 카드까지 시각적으로 검증 (API 키가 있을 때의
   동작은 `fetch`를 모킹해 재현)
5. **② 지역 우선 선택 모드 전체 플로우 검증**: MOLIT API와 Nominatim 지오코딩을 모두
   모킹해 "지역 선택 → 예산 자동 계산(실제 실거래 샘플 기준) → 예산 범위로 하드 필터링된
   매물 검색 → 지오코딩 성공/실패 혼합 상황에서 좌표 부여 → 목록 클릭 시 상세 정보 펼침 +
   지도 확대"까지 Playwright로 화면을 캡처하며 검증. 조건에 맞는 매물이 하나도 없는
   경우에도 에러 없이 안내 문구만 표시되는지 별도 확인.
6. **매물 "다트 착지" 애니메이션 검증**: 위와 동일하게 API를 모킹해 매물 검색 결과가
   도착한 직후 지도 위 마커들이 `dart-outer-animate` 클래스와 함께(순서대로 130ms씩
   지연된 `animation-delay`) 생성되는지 DOM에서 직접 확인하고, 애니메이션 진행 중/완료
   시점을 Playwright로 캡처해 다트 핀 모양 마커가 예상 위치에 정상 착지하는지 검증.
   후보를 클릭해 선택 상태만 바뀌는 재렌더링에서는 `dart-outer-animate` 클래스(및 사운드/
   진동 예약)가 다시 붙지 않는 것도 코드 경로상 확인. 사운드(Web Audio API 합성음)와
   진동(`navigator.vibrate`)은 스크린샷으로 직접 들리거나 느껴지는 것을 확인할 수는
   없어, 재생을 예약하는 함수가 올바른 타이밍에 호출되는지까지만 검증했습니다 — 실제
   사운드/진동 체감은 브라우저에서 직접 확인해 주세요.

**발견 후 수정한 버그**: ② 모드에서 "매물 찾기" 버튼을 눌러도 아무 반응 없이 화면이
그대로였던 문제가 있었습니다. 원인은 자동 계산된 예산값(예: `6.75`억원)이 예산 입력칸의
HTML `step="0.1"` 제약과 맞지 않아, 브라우저가 폼 제출 자체를 조용히 막고 있었기
때문입니다(콘솔 에러 없이 브라우저 자체 유효성 검사 말풍선만 뜨고 `onSubmit`이 아예
호출되지 않음). 예산 입력칸의 `step`을 `any`로 바꿔 어떤 소수점 값이 자동 채워져도
제출이 막히지 않도록 수정했고, 같은 문제가 있던 ① 모드의 목표 예산 입력칸도 함께
고쳤습니다. 수정 후 API 키가 없는 상태에서도 "매물 찾기" 클릭 시 매물 후보 패널이
정상적으로 나타나는 것을 Playwright로 재확인했습니다.

**두 번째로 발견 후 수정한 버그**: ② 모드에서 실제 서비스키를 등록했는데도 지도와 매물
목록이 계속 "빈 지도"로만 나오는 문제가 있었습니다. 원인은 `lib/molit.js`가 국토부 API의
HTTP 상태코드(`res.ok`)만 확인하고 있었던 것입니다 — 공공데이터포털은 서비스키가 아직
승인 대기 중이거나 잘못된 키(Encoding/Decoding 키 혼동)를 쓰면 **HTTP 200 정상 응답이지만
본문은 오류 메시지인 XML**(`<cmmMsgHeader><returnAuthMsg>...`)을 돌려주는데, 기존 코드는
이 응답에서 `<item>` 태그를 찾지 못하면 그냥 "매물 0건"으로 조용히 처리해 버려서 진짜
원인(인증 실패)이 화면 어디에도 보이지 않았습니다. `callApi`에 `detectApiError()`를 추가해
이런 오류 응답을 감지하면 명확한 한국어 메시지로 예외를 던지도록 고쳤고, 이 예외가
② 모드의 예산 계산 단계(`estimateError`)와 매물 검색 단계(`candidateError`) 양쪽 화면에
바로 표시되도록 API 응답과 컴포넌트를 함께 수정했습니다. `global.fetch`를 공공데이터포털의
실제 인증 오류 응답 형태로 모킹해 estimate/search 두 엔드포인트 모두 이제 원인 메시지를
정확히 반환하는 것을 확인했고, 정상 응답 모킹으로도 회귀가 없는지(매물 목록·지도 핀·다트
애니메이션까지) 다시 검증했습니다. 참고로 반대로 정상 동작할 때(달마다 일시적인 네트워크
오류가 한 번 있는 경우)는 여전히 그 달만 건너뛰고 나머지 달로 계속 진행하도록 구분해
두었습니다(인증/서비스 오류만 즉시 위로 전달).

모두 통과를 확인했으며, 국토부 아파트 실거래가 API와 Nominatim 지오코딩은 실제 서비스키·
실제 네트워크로 라이브 테스트는 하지 못했습니다(이 환경은 국토부 API 키 발급이 불가능하고,
외부 지도 타일 접속도 제한되어 있습니다) — §4 안내대로 키를 발급받아 직접 연동을 확인해
주세요. 지도 자체(마커 표시, 클릭 상호작용, 줌/이동)는 정상 동작을 확인했고, 실제 배포
환경에서는 OpenStreetMap 타일이 정상적으로 로드됩니다.

## 9. 전국 확장 + 전월세 + 예산 백분위 개편 (이번 라운드) 검증

이번 개편(①거래유형 매매/전세/월세 구분, ②아파트/주상복합 분리는 보류, ③예산 범위
백분위 계산, ④전국 250개 이상 지역 확장)에 대해 진행한 검증입니다.

1. **데이터 정합성 검증**: `lib/districts.js`의 250개 항목을 스크립트로 순회해
   `lawdCd` 중복 없음, 5자리 숫자 형식 준수, 필수 필드 누락 없음, 좌표가 대한민국
   범위(위도 32~39, 경도 123~132) 안에 있음, 서울 25개 구는 기존 값과 100% 동일함을
   확인했습니다. `groupDistrictsBySido()`가 17개 시/도로 정확히 묶는 것도 확인했습니다.
2. **`npm run build` 성공 확인**: 손으로 조립한 250개 항목짜리 `lib/districts.js`를
   포함해 전체 프로젝트가 문법 오류 없이 정상 빌드되는 것을 확인했습니다.
3. **① 모드 — 전국 랭킹 + 미조사 지역 중립값 폴백 (Playwright)**: API 키 없이(참고값
   폴백 경로) 기본 조건(강남역, 서울 인근 직장)으로 실행하면 서울 25개 구가 상위권을
   차지하는 것을 확인했고, 직장 위치를 부산 좌표로 바꾸고 통근시간 가중치를 높이면
   부산 지역(아직 조사되지 않은 지역)이 상위 10위에 오르면서도 화면이 깨지지 않고
   "참고값 없음"/"미조사"가 정직하게 표시되며 실제 통근시간(직선거리 기반)까지 정상
   계산되는 것을 확인했습니다(부산광역시 연제구가 1위, 14분으로 계산됨).
4. **② 모드 — 시/도별 그룹 드롭다운 + 거래유형 전환 (Playwright)**: 드롭다운이 17개
   시/도 optgroup, 총 250개 옵션으로 정상 렌더링되는 것을 확인했습니다. 거래유형을
   매매→월세로 바꾸면 예산 입력란 라벨이 "필요 보증금(월세는 매물별로 별도 표시)"로
   즉시 바뀌는 것을, 서울 외 미조사 지역(춘천시)을 선택하면 "참고값이 아직 없습니다"
   안내가 뜨고 예산 입력란은 빈 채로(강제로 채우지 않고) 유지되는 것을 확인했습니다.
5. **월세 후보 표시 + 백분위 기반 예산 범위 (Playwright, API 모킹)**: `/api/district-search`
   응답을 모킹해 표본 8건짜리 백분위 기반(`percentileBased: true`) 예산 범위와 월세
   매물(보증금 2억 · 월세 85만원) 카드가 화면에 정확한 문구("최근 실거래 8건 중 상하위
   10%를 제외한 실제 범위입니다", "보증금 2억 · 월세 85만원")로 렌더링되는 것을

6. **`lib/scoring.js` null-안전성**: `pricePerPyeong`/`schoolIndex`/`safetyIndex`/
   `amenityIndex`가 `null`인 지역에서 `NaN`이 발생하지 않고 중립값 50점으로 대체되는지,
   `lawdCd` 기준 매칭이라 이름이 같은 지역(예: 여러 "중구")이 서로 뒤섞이지 않는지
   위 3번 테스트로 실측 확인했습니다.

**설계상 알아둘 점**: `lib/molit.js`의 전월세 API 3종(`rentUrl`)은 문서 조사만으로
구성했고 실제 서비스키로 라이브 검증은 못 했습니다 — §4/§7 안내대로 실제 연동 후 응답이

그대로이며(§5-1), 이번 라운드에서는 의도적으로 채우지 않고 정직하게 "미조사"로 남겨
두었습니다.

## 10. 실제 서비스키로 처음 검증하면서 발견 후 수정한 버그 3건

이 프로젝트는 개발 환경 자체가 국토부 API 서버(`apis.data.go.kr`)로 나가는 네트워크
요청을 차단하고 있어서, 여기까지의 모든 "테스트 통과"는 전부 직접 만든 가짜(mock)
응답으로 화면·로직만 검증한 것이었습니다. 사용자가 실제 서비스키로 앱을 직접 실행해보고
공공데이터포털 공식 기술문서(아파트 매매 실거래가 자료)까지 공유해 준 덕분에, 실제 API와
비교해서만 발견할 수 있었던 버그 3건을 찾아 고쳤습니다.

1. **단지명이 항상 "단지명 미상"으로 나오는 버그**: 실제 서비스키로 매물 후보를 조회하면
   가격·평형·법정동은 정상인데 단지명만 항상 "단지명 미상"으로 나왔습니다. 처음에는
   응답이 CDATA로 감싸져 있을 거라 추측해 파싱 정규식을 고쳤지만, 사용자가 공유해 준
   공식 기술문서의 "구 API/신규 API 코드 신구대조표"를 확인해보니 **진짜 원인은 훨씬
   단순**했습니다 — 신규 아파트매매 API는 단지명 필드를 `aptNm`이라는 태그로 주는데,
   `TAG_CANDIDATES.complexName` 후보 목록에는 `"아파트"`, `"단지명"` 같은 한글 태그만 있고
   실제 태그인 `aptNm`이 아예 빠져 있었습니다. 가격(`dealAmount`)·평형(`excluUseAr`)·
   법정동(`umdNm`) 등은 우연히 영문 후보가 이미 목록에 있어서 정상 동작했던 것뿐이었고,
   단지명만 이 문제를 피해가지 못했던 것입니다. 문서로 확인된 신규 API 영문 태그를
   1순위 후보로 넣어 고쳤고, 실제 API 응답과 동일한 형태의 XML(`aptNm`, `dealAmount`,
   `excluUseAr` 등 camelCase 태그)로 `lib/molit.js`의 실제 함수(`fetchRecentListings`)를
   그대로 실행해 단지명이 정확히 파싱되는 것을 확인했습니다. (CDATA 처리 자체는 이 문서의
   예제 응답에는 나타나지 않아 실제로 필요했는지는 불확실하지만, 있어도 해가 되지 않는
   방어적 코드라 그대로 남겨두었습니다.)
2. **전국 랭킹(① 모드)에서 일부 지역의 매물 후보를 못 불러오는 HTTP 429 오류**: 서울
   서초구·송파구 등 일부 지역에서 "국토부 실거래가 API가 HTTP 429 오류를 반환했습니다"가
   나타났습니다. 원인은 전국 확장 때문입니다 — ① 모드는 전국 250개 이상 지역의 참고
   평당가를 `Promise.all`로 한꺼번에 조회하는데, 국토부 기술문서에 명시된 "초당 최대
   트랜잭션 30tps"를 크게 초과해서 요청을 보내고 있었습니다(서울 25개 구만 다루던 이전
   버전에서는 잘 드러나지 않았던 문제입니다). `lib/molit.js`에 모든 국토부 API 요청이
   거쳐가는 공용 요청 큐를 추가해 "새 요청 시작"을 초당 최대 20건으로 제한하고, 그래도
   429가 오면 지수 백오프(0.5→1→2초)로 최대 3번 자동 재시도하도록 고쳤습니다. `fetch`를
   모킹해 (a) 429 응답이 두 번 온 뒤 세 번째 시도에서 성공하는 상황에서 백오프 타이밍이
   정확한지, (b) 지역 40곳을 동시에 조회해도 실제 요청 시작 속도가 초당 20건을 넘지 않는지
   직접 측정해 확인했습니다.
3. **주택유형별로 활용신청이 따로 필요하다는 것을 안내하지 않던 문제**: 아파트는 정상
   동작하는데 오피스텔만 골라서 검색하면 강남구·서초구·송파구 등에서 "국토부 실거래가
   API가 HTTP 403 오류를 반환했습니다"만 뜨고 왜 그런지는 알 수 없었습니다. 공공데이터
   포털은 서비스키 하나를 발급받아도 **데이터셋(주택유형·매매/전월세)마다 활용신청을
   따로** 해야 하는데(§4에 이미 안내되어 있던 내용입니다), 그동안 코드는 이 경우를
   "HTTP 403 오류를 반환했습니다"라는 상태코드만 보여주고 원인은 설명하지 않아서
   사용자가 직접 §4 안내를 다시 찾아 유추해야 했습니다. 이제 HTTP 403/401 응답을 별도로
   구분해서 "이 데이터셋만 활용신청이 안 되어 있거나 미승인 상태일 수 있고, 다른 주택
   유형이 정상 동작한다면 서비스키 자체는 문제가 없다"는 원인과 확인 위치(마이페이지 >
   개발계정)까지 메시지에 직접 담도록 고쳤습니다. `fetch`를 403/401 응답으로 모킹해
   메시지가 정확히 나오는지 확인했습니다.

**참고로 이 오피스텔 403 자체는 버그가 아니라 정상적인 동작입니다** — 오피스텔 매매
데이터셋의 활용신청/승인이 아직 안 되어 있다면 실제로 이 오류가 나는 게 맞습니다.
data.go.kr 마이페이지에서 "국토교통부_오피스텔 매매 실거래자료"의 활용신청 상태를
확인해 주세요(§4의 신청 목록 참고). 신청 후 보통 즉시~수 분 내 승인되지만, 계정 상황에
따라 더 걸릴 수 있습니다.

**오피스텔 매매 API 필드명 재검증 (버그 아님, 확인 완료)**: 사용자가 오피스텔 매매
실거래가 자료 공식 기술문서도 공유해 준 덕분에 실제 필드명을 대조해봤는데, 다행히 이
API는 이미 정확하게 구현되어 있었습니다 — 응답 태그가 `offiNm`(단지명), `sggNm`(시군구)
등 아파트와 살짝 다르지만, `offiNm`은 이미 `TAG_CANDIDATES.complexName` 후보 목록에
들어 있어서 별도 수정이 필요 없었습니다. 문서에 실린 요청/응답 예제(`용비어천가`,
`25,200`만원, `내수동` 등)를 그대로 재현한 XML로 `fetchRecentListings`를 실행해 모든
필드(단지명·거래금액·전용면적·법정동·건축년도·층)가 정확히 파싱되는 것을 확인했습니다.
(참고: 이 문서 자체에 "상세기능명(영문)"란이 `getRTMSDataSvcAptRent`로 잘못 적혀 있는
오타가 있었지만, 바로 아래 Call Back URL과 실제 요청/응답 예제는 모두 정확히
`RTMSDataSvcOffiTrade/getRTMSDataSvcOffiTrade`를 가리키고 있어 우리 코드의 URL이
맞다는 것도 함께 확인했습니다.) 이로써 아파트·오피스텔 매매 두 API는 공식 문서로
검증 완료된 상태이고, 연립다세대 매매와 아파트·오피스텔 전월세 API만 아직 미검증으로
남아 있습니다.

**연립다세대 전월세 API 필드명 재검증 (버그 아님, 확인 완료)**: 연립다세대 전월세 실거래가
자료 공식 기술문서도 공유해 준 덕분에 확인해봤는데, 이 API 역시 이미 정확하게 구현되어
있었습니다. 신규 API 필드는 `deposit`(보증금액)·`monthlyRent`(월세금액)·`mhouseNm`
(연립다세대명) 등인데, 셋 다 `TAG_CANDIDATES`에 이미 후보로 들어 있던 이름과 정확히
일치했습니다(당시엔 추정으로 넣어둔 것이었는데 운 좋게 맞았습니다). 문서에 실린 요청/응답
예제(보증금 70,000만원, 월세금액 0 = 전세, 북악더테라스2단지, 신영동 등)를 그대로 재현한
XML로 `fetchRecentListings`를 실행해 (1) 전세 조건(`dealType: "jeonse"`)일 때 이 예제가
정상적으로 포함되고, (2) 월세 조건(`dealType: "wolse"`)일 때는 월세금액이 0이라 정확히
걸러지는 것까지 확인했습니다. 이제 아파트·오피스텔 매매, 연립다세대 전월세까지 3개 API가
공식 문서로 검증 완료되었고, 연립다세대 매매와 아파트·오피스텔 전월세 API 3종만 미검증
상태입니다.

**연립다세대 매매 API 필드명 재검증 (버그 아님, 확인 완료)**: 연립다세대 매매 실거래가
자료 공식 기술문서도 확인했는데, 이 API도 이미 정확하게 구현되어 있었습니다. 신규 API
필드는 `dealAmount`(거래금액)·`excluUseAr`(전용면적)·`mhouseNm`(단지명)·`umdNm`(법정동)
등인데 전부 `TAG_CANDIDATES`에 이미 들어 있는 이름과 일치했습니다. 문서 예제(거래금액
36,900만원, 현진빌라B동, 숭인동, 전용면적 57.21㎡)를 그대로 재현한 XML로
`fetchRecentListings`를 실행해 모든 필드가 정확히 파싱되는 것을 확인했습니다. (참고: 이
문서의 "상세기능명(영문)"란도 `getRTMSDataSvcAptRent`로 오타가 있었지만 Call Back URL과
실제 예제는 `RTMSDataSvcRHTrade/getRTMSDataSvcRHTrade`를 정확히 가리키고 있어 코드의
URL이 맞다는 것도 확인했습니다. 이 문서에서 새로 발견한 `landAr`(대지권면적) 필드는 현재
앱 기능에 쓰이지 않아 추가하지 않았습니다.)

**오피스텔 전월세 API 필드명 재검증 (버그 아님, 확인 완료)**: 오피스텔 전월세 실거래가
자료 공식 기술문서도 확인했는데, 이 API 역시 이미 정확했습니다. `deposit`·`monthlyRent`·
`offiNm`(단지명) 모두 기존 후보 목록과 일치했습니다. 문서 예제(보증금 19,400만원, 월세
0=전세, 한라 운종가, 숭인동)를 재현한 XML로 전세/월세 필터링까지 정확히 동작하는 것을
확인했습니다.

**아파트 전월세 API 필드명 재검증 (버그 아님, 확인 완료)**: 아파트 전월세 실거래가 자료
공식 기술문서도 확인했는데, 이 API도 이미 정확했습니다. 단지명 필드가 `aptNm`인데,
이미 §10-1에서 매매 API의 "단지명 미상" 버그를 고치면서 `aptNm`을 후보 1순위로 넣어둔
덕분에 전월세 API도 함께 정확히 동작합니다. 문서 예제(보증금 50,000만원, 월세 0=전세,
두산, 창신동)를 재현한 XML로 전세/월세 필터링까지 확인했습니다. (이 문서에서 새로 발견한
`aptSeq`/`roadnm`류 도로명 필드들도 현재 앱 기능에는 쓰이지 않아 추가하지 않았습니다.)

이로써 국토부 실거래가 API **6개 데이터셋(아파트·연립다세대·오피스텔 × 매매·전월세) 전부**
공식 기술문서로 필드명·서비스 URL 검증을 마쳤습니다.

## 11. ① 모드("어디로 갈지 추천받기") 지도 우선 UX 개편

사용자가 실제로 써 보면서 "직장 드롭다운으로 위치를 고르는 것보다 지도를 먼저 보여주고,
지도에서 직접 중심점과 반경을 고르는 게 더 자연스럽지 않냐"는 피드백을 주셔서, ① 모드의
입력 흐름을 아래처럼 다시 짰습니다.

1. **지도가 조건 입력보다 먼저 나옵니다.** 예전에는 "직장 위치" 드롭다운이 첫 번째 입력
   이었는데, 이제는 지도가 폼 맨 위에 바로 나오고 드롭다운은 없앴습니다. 페이지가 열리면
   `navigator.geolocation`으로 조용히 내 위치를 확인해 파란 점(맥동 애니메이션)으로
   표시하고(권한 거부/실패 시에는 에러 문구 없이 기본 위치를 그대로 씁니다 — 아무 것도
   안 눌렀는데 에러가 뜨면 당황스러우니까요), 지도를 클릭하면 그 지점이 검은 다트 핀으로
   검색 중심점이 됩니다. 예전 직장 드롭다운에 있던 9개 업무지구는 지도 아래 빠른 선택
   칩 버튼으로 남겨 뒀습니다(클릭 한 번으로 지도가 그 위치로 부드럽게 이동).
2. **반경 검색 vs 시/도 검색을 탭으로 전환**합니다. "반경으로 찾기"를 고르면 3~50km
   슬라이더가 나오고, 슬라이더를 옮길 때마다 "반경 OOkm 안 OO개 지역"이라고 실시간으로
   몇 개 지역이 걸리는지 보여줍니다(클라이언트에서 바로 계산 — API 호출 없음). "시/도로
   찾기"를 고르면 17개 시/도 드롭다운으로 바뀝니다. 백엔드(`app/api/recommend/route.js`)는
   이렇게 좁혀진 지역군(`poolDistricts`) 안에서만 랭킹과 실거래 조회를 수행하도록
   바꿨습니다 — 예전에는 항상 전국 250개 이상을 다 조회했는데, 이제는 보통 수십 개로
   줄어서 API 호출 수도 줄고(429 위험도 더 낮아짐) 결과도 사용자가 지정한 범위 안으로
   좁혀집니다. 반경이 너무 좁아 지역이 하나도 안 걸리면(도서산간 등) 가장 가까운 10개
   지역으로 자동 대체합니다.
3. **예산/평형은 숫자 입력 대신 범위 슬라이더로 고릅니다.** 처음에는 가로로 스크롤하는
   단일 값 피커(`ScrollPicker`)였는데, 이후 네이버 부동산류 최소/최대 듀얼 손잡이 슬라이더
   (`RangeSlider`)로 다시 바꿨습니다 — 자세한 내용은 아래 12장을 참고하세요.
4. **"상세 조건" 섹션은 슬라이드로 접고 펼칠 수 있습니다.** 거래유형·주택유형·준공연식·
   방/화장실·예산·평형·가중치 슬라이더가 모두 이 안에 들어가고, 버튼 하나로
   보였다 안 보였다 전환됩니다(CSS `grid-template-rows` 트랜지션 — 라이브러리 없이 순수
   CSS로 부드럽게 접힙니다).
5. **"이사 갈 곳 추천받기" 클릭 시 연출**: 지도가 검색 중심점으로 `flyTo`로 부드럽게
   확대되면서 기존에 ②모드에서만 쓰던 "다트가 파팍 꽂히는" 애니메이션+소리를 그대로
   재사용해 재생하고, 이후 최소 약 1.3초는 "OO 지역들을 비교하고 있어요..." 문구를
   유지한 뒤 결과를 보여줍니다(실제 API가 더 빨리 응답해도 이만큼은 기다립니다) — 결과가
   튀어나오듯 나오지 않고 "분석 중"이라는 느낌을 주기 위한 의도적인 지연입니다.
6. **결과 지도 마커는 여전히 지역(구/동) 단위 대표 마커입니다.** 국토부 실거래 데이터에는
   정확한 주소가 없어 "법정동"까지만 알 수 있기 때문에, 매물 하나하나에 마커를 찍으면
   같은 동의 여러 매물이 지도상 거의 같은 위치에 겹쳐 찍히게 됩니다 — 그래서 지역 단위
   대표 마커(지금과 동일한 방식)를 유지하기로 했습니다(개별 매물 위치가 실제로 필요한
   ②모드는 이미 Nominatim 지오코딩으로 단지 단위 마커를 보여주고 있습니다).
7. **지도 확대/축소가 마우스 휠로도 가능**해졌습니다(이전에는 페이지 스크롤과의 충돌을
   피하려고 꺼 두었는데, 요청에 따라 켰습니다 — 두 손가락 핀치 확대는 원래도 가능했습니다).
8. **매물 후보마다 "네이버 부동산에서 보기" 링크**가 붙습니다(①·② 모드 모두). 정확한
   주소가 없어 특정 매물로 바로 연결되는 딥링크는 불가능하고, 법정동+단지명으로 네이버
   부동산 검색 결과 페이지로 연결합니다.
9. **모바일 화면 최적화**: 640px 이하에서 여백·글자 크기·지도 높이가 자동으로 줄고, 제출
   버튼과 칩 버튼들은 터치하기 쉬운 크기(최소 38~44px)로 커집니다.

검증은 Playwright로 진행했습니다: 지도/칩/반경 슬라이더/시·도 토글/상세조건 접기·펼치기/
예산·평형 피커 조작/제출 시 서스펜스 문구 노출까지 실제 브라우저에서 클릭해 확인했고,
반경 검색·시/도 검색 각각 API 응답의 `districtPoolSize`가 예상대로 좁혀지는지(서울 시청
반경 15km → 28개 지역, 부산광역시 시/도 선택 → 16개 지역), 반경이 너무 좁을 때 최근접
10개 지역으로 대체되는지(제주 남쪽 바다 좌표로 반경 3km 검색 → 10개 지역 폴백)도 직접
요청을 보내 확인했습니다. 서울이 아닌 지역(부산)을 시/도로 검색해도 학군/치안 참고지수가
없는 지역이 "미조사"로 안전하게 표시되며 앱이 죽지 않는 것도 함께 확인했습니다.

## 12. 목표예산·평형 선택을 네이버 부동산류 범위 슬라이더로 교체

사용자가 네이버 부동산 필터 화면(최소/최대 두 손잡이로 가격·면적 구간을 고르는 슬라이더)
스크린샷을 보여주며 "목표예산·평형 선택도 이 모양으로 바꿔달라"고 요청해서, 11장에서 만든
가로 스크롤 단일 값 피커(`ScrollPicker`, 목표값 하나 + 허용 오차 방식)를 완전히 걷어내고
최소/최대를 각각 지정하는 듀얼 손잡이 범위 슬라이더(`RangeSlider`)로 바꿨습니다.

1. **`app/components/RangeSlider.js`(신규)**: `<input type="range">` 두 개를 같은 트랙
   위에 겹쳐서 그리는 흔한 구현 방식입니다. 트랙 자체는 클릭해도 반응하지 않도록
   CSS에서 `pointer-events`를 손잡이(`::-webkit-slider-thumb`/`::-moz-range-thumb`)에만
   허용하고, 두 `<input>`의 트랙은 투명하게 비활성화했습니다 — 그래야 최소/최대 손잡이를
   서로 방해 없이 각각 드래그할 수 있습니다. 마지막으로 잡은 손잡이의 `z-index`를 높여서
   두 손잡이 값이 같아져도 계속 움직일 수 있게 했고, 초록색 채움 막대·눈금(예: "최소 10억
   20억 30억 최대")은 스크린샷 디자인을 그대로 따랐습니다. `ScrollPicker.js`는 더 이상 쓰는
   곳이 없어 삭제했고, 관련 CSS(`.scroll-picker*`)도 함께 정리했습니다.
2. **"손잡이가 양 끝에 있으면 = 전체(범위 지정 없음)" 규칙**: 목표예산은 0~40억,
   평형은 0~60평 범위의 슬라이더인데, 손잡이가 그 끝(0 또는 40/60)에 그대로 있으면
   "그쪽 경계는 지정하지 않음"으로 취급합니다. 이 규칙은 프런트(`RankFlow.js`의
   `BUDGET_FLOOR/CEIL`, `PYEONG_FLOOR/CEIL`)와 백엔드(`app/api/recommend/route.js`의
   동일한 이름의 상수)에 각각 따로 정의되어 있고, 두 값이 반드시 같아야 하므로 양쪽 파일에
   "같이 맞춰야 한다"는 주석을 남겨 뒀습니다. 둘 다 "전체"면 헤더에 "전체", 한쪽만 지정하면
   "10억 이상"/"20억 이하"처럼, 둘 다 지정하면 "10~20억"처럼 표시됩니다.
3. **점수·필터링 로직을 "목표값+오차" 방식에서 "범위" 방식으로 다시 짰습니다.**
   - `lib/scoring.js`의 `budgetFitScore`는 이제 `budgetMin`/`budgetMax` 두 값을 받습니다.
     예상 총액이 범위 안에 들어오면 92~100점(범위 중앙에 가까울수록 높음), 범위 밖이면
     벗어난 정도에 비례해 점수가 깎입니다. 범위가 "전체"(둘 다 미지정)이면 중립값 50점을
     줍니다.
   - `lib/candidates.js`의 `findCandidates`는 `pyeongMin`/`pyeongMax`를 받으면 그 범위를
     그대로 면적 필터로 쓰고, (② 모드처럼) 기존 방식으로 단일 `pyeong`만 넘어오면 이전과
     동일하게 ±22% 오차를 적용합니다 — ② 모드(`DistrictFlow`)는 코드를 손대지 않았습니다.
   - `app/api/recommend/route.js`는 요청 바디를 `budgetEok`/`pyeong` 단일 값 대신
     `budgetMin`/`budgetMax`/`pyeongMin`/`pyeongMax` 네 값으로 받고, 지역별 "예상 총액"
     랭킹 계산에 쓸 평형 대표값은 범위의 중앙값(평형이 "전체"면 기본값 25평)을 사용합니다.
     응답 `meta`에도 이 네 값을 그대로 돌려줍니다.

검증은 Playwright로 새로 진행했습니다: 기본 상태에서 두 슬라이더 모두 "전체"로 표시되는지,
키보드(방향키)로 최소 손잡이만 움직이면 헤더가 "OO억 이상"으로 바뀌는지, 최대 손잡이를
최소값 아래로 내리려 해도 최소값을 넘어가지 않고 멈추는지(클램핑), 스크린샷이 참고 디자인과
시각적으로 일치하는지 확인했습니다. `/api/recommend`에 직접 요청을 보내 범위를 지정한
경우(예산 10~20억)와 "전체"로 둔 경우 각각 `meta.budgetMin/budgetMax/pyeongMin/pyeongMax`
값과 `breakdown.price` 점수가 계산식대로 나오는지도 확인했고, 11장에서 만든 지도/칩/반경
슬라이더/시·도 토글 회귀 테스트도 다시 돌려 콘솔 에러 없이 통과하는 것을 확인했습니다.

## 13. 서비스키를 설정했는데도 "매물 후보 0건"이 나오는 문제 — 진단 로그 추가

시/도 검색(서울특별시)으로 실행했을 때 상단 배지는 "실거래가 실시간 연동 중"으로 뜨는데도
(=서비스키는 인식됨) 강남구처럼 거래가 활발한 구조차 "예상 시세"가 조사 참고값으로만
나오고, 모든 지역의 "실제 매물 후보"가 하나도 안 뜨는 문제를 사용자가 스크린샷으로
알려줬습니다. 화면에는 별도 에러 박스도 없이 그냥 "조건에 맞는 최근 거래를 찾지 못했습니다"
문구만 조용히 떠 있어서, 원인이 (a) 인증/활용신청 문제인지 (b) 그 달에 정말 거래가 없는
건지 (c) 실제 응답 필드명이 검증 당시 문서와 달라져 파싱이 실패하는 건지 구분할 방법이
전혀 없었습니다 — `lib/molit.js`의 `fetchAvgPricePerPyeong`은 어떤 에러든 조용히 `continue`
하고 3개월을 다 실패하면 그냥 `null`을 반환하도록 되어 있어서, 콘솔에 아무 흔적도 남기지
않았습니다(개발 환경 자체가 국토부 API 서버로 나가는 요청을 막고 있어 이 세션에서는 실제
서비스키로 재현해 원인을 확정할 수 없었습니다).

그래서 원인을 바로 확정하는 대신, `lib/molit.js`에 진단용 로그를 추가했습니다. 다음에
같은 증상이 나오면 `npm run dev`(또는 `next start`)를 띄운 터미널 창에 `[molit]`로 시작하는
줄이 찍히는데, 이 로그만 보면 원인이 셋 중 무엇인지 바로 구분됩니다.

- `[molit] ... → totalCount=N, 파싱된 유효 거래=M건` — 매 API 호출마다 한 줄씩 남습니다.
  `totalCount`가 0이면 국토부 쪽에 그 달 데이터가 정말 없다는 뜻이고, `totalCount`는
  0보다 큰데 `M`(파싱된 거래)이 0이면 API는 데이터를 줬는데 우리 코드가 필드를 못 읽고
  있다는 뜻이라 필드명 문제로 바로 좁혀집니다.
- `XML에 <item> N건이 있었지만 파싱된 유효 거래는 0건입니다` — 바로 위 "필드명 문제"
  상황에서 응답 XML 앞부분(800자)을 함께 남겨서, 실제 태그명이 뭔지 바로 눈으로 확인할 수
  있습니다.
- `... 평균가 조회 실패: <에러 메시지>` / `... 매물 조회 실패: <에러 메시지>` — 인증 오류
  (서비스키 미승인 등)나 HTTP 403/429처럼 명확한 에러가 났을 때 그 메시지를 그대로
  남깁니다(전에는 이 경우도 조용히 다음 달로 넘어가기만 하고 아무것도 남기지 않았습니다).
- `... 표본 N건(<5) — 평균가 계산에 부족해 다음 달로 넘어갑니다` — 에러는 아니지만 그 달
  표본이 통계적으로 너무 적어(5건 미만) 건너뛰는 정상적인 경우도 구분되게 남깁니다.

가짜 응답(정상/필드명 다름/데이터 없음/인증오류/403)을 각각 흉내 낸 유닛 테스트로 다섯
시나리오 모두 의도한 로그와 반환값이 나오는 것을 확인했습니다. 이 변경은 로그만 추가한
것이라 기존 동작(점수 계산, 후보 필터링, 화면 표시)은 전혀 바뀌지 않았고, 11~12장의 회귀
테스트도 다시 돌려 콘솔 에러 없이 통과하는 것을 확인했습니다.

**다음에 같은 문제가 재현되면, 검색을 실행한 직후 터미널에 찍히는 `[molit]` 로그를 그대로
캡처해서 알려주세요** — 그 내용만 보면 정확한 원인(활용신청 미승인/이번 달 데이터 없음/
필드명 변경)을 바로 짚어서 고칠 수 있습니다.

### 13-1. 실제로 캡처된 로그로 원인 확정: 서버가 국토부 API 서버에 아예 접속하지 못하는 상태

사용자가 위 로그를 캡처해서 보내준 덕분에 원인이 바로 나왔습니다. 모든 지역·모든 달의
요청이 예외 없이 다음과 같이 실패하고 있었습니다.

```
[molit] 11680 apt/trade 202609 매물 조회 실패: fetch failed
```

`"fetch failed"`는 국토부 API가 403/429처럼 **응답을 주긴 했는데 거부한** 상황이 아니라,
**요청이 서버에 도달하지도 못했다는** Node.js(정확히는 내부 `undici` fetch 구현체)의 아주
뭉뚱그려진 오류 메시지입니다. 즉 인증키·활용신청 문제가 아니라, 이 앱을 실행 중인 서버가
`apis.data.go.kr`로 나가는 네트워크 요청 자체를 못 하고 있다는 뜻입니다(방화벽, 사내/기관
프록시, DNS 문제 등이 흔한 원인입니다). 25개 지역이 전부, 매매·평균가 요청과 매물 후보
요청 양쪽 다 예외 없이 이 메시지만 반복된 것도 "일부 API만 막힘"이 아니라 "바깥으로 나가는
연결 자체가 막힘"이라는 정황과 맞습니다.

문제는 `"fetch failed"`라는 메시지만으로는 진짜 원인(DNS 조회 실패인지, 연결 거부인지,
타임아웃인지)까지는 알 수 없다는 점이었습니다 — Node의 fetch는 진짜 원인을 `err.cause`
(경우에 따라 그 안에 또 `cause`)에 담아두는데, 기존 로그는 `err.message`만 남겨서 이
`cause`가 잘려 나가고 있었습니다. 그래서 `lib/molit.js`에 `describeError()`를 추가해
`cause` 체인을 최대 3단계까지 따라가며 `code`(예: `ENOTFOUND`, `ECONNREFUSED`, `ETIMEDOUT`)
와 메시지를 함께 남기도록 고쳤습니다 — 다음 로그부터는 `fetch failed / 원인: ENOTFOUND —
getaddrinfo ENOTFOUND apis.data.go.kr`처럼 구체적인 원인까지 한 줄에 보이게 됩니다.

또한 `fetchRecentListings`(매물 후보 조회)가 이런 순수 네트워크 오류를 `MolitServiceError`가
아니라는 이유로 조용히 빈 배열로 넘겨버리는 문제도 함께 고쳤습니다 — 조회한 달이 "전부"
정상 응답이 아니라 에러로 실패한 경우(=데이터가 없어서가 아니라 요청 자체가 실패한 경우)는
이제 명확한 에러로 묶어 호출부까지 전달합니다. 그 결과 화면에도 그냥 "조건에 맞는 거래를
찾지 못했습니다"가 아니라, "일부 지역의 매물 후보를 불러오지 못했습니다" 에러 박스에 원인
(네트워크 문제일 가능성과 확인 방법 포함)이 직접 표시됩니다. (평균가 조회 쪽은 원래도
개별 지역 하나가 실패해도 조사 참고값으로 조용히 폴백하는 게 의도된 설계라 이 부분은
그대로 두고 로그만 보강했습니다.)

`err.cause`가 있는/없는 순수 네트워크 오류를 흉내 낸 가짜 `fetch`로 (1) `describeError`가
원인을 정확히 풀어내는지, (2) 모든 달이 이런 오류로 실패하면 `fetchRecentListings`가 빈
배열 대신 명확한 에러를 던지는지 유닛 테스트로 확인했고, 11~13장 회귀 테스트도 다시 돌려
콘솔 에러 없이 통과하는 것을 확인했습니다.

**사용자가 직접 확인해 볼 것**: 이 앱 서버를 실행 중인 바로 그 기기의 터미널에서
`curl -v https://apis.data.go.kr` 를 실행해 접속이 되는지 확인해 주세요. 안 된다면 사내망/
공유기 방화벽이 이 주소를 막고 있거나, 그 네트워크가 별도 프록시 설정을 요구하는 상황일
가능성이 높습니다(회사·기관 네트워크에서 흔합니다). 반대로 `curl`은 되는데 앱에서는 여전히
"fetch failed"가 난다면, 브라우저/curl은 시스템 프록시 설정을 자동으로 타는데 Node.js의
`fetch`는 `HTTP_PROXY`/`HTTPS_PROXY` 환경변수를 자동으로 쓰지 않기 때문일 수 있습니다 —
이 경우라면 알려주시면 Node 쪽에 프록시를 명시적으로 연결하는 코드를 추가해 드리겠습니다.

### 13-2. 진짜 원인 확정: TLS 검사(SSL inspection)로 인한 자체 서명 인증서 — 해결

사용자가 보강된 로그를 다시 캡처해 준 덕분에 정확한 원인이 나왔습니다.

```
[molit] 11680 apt/trade 202609 매물 조회 실패: fetch failed / 원인: SELF_SIGNED_CERT_IN_CHAIN — self-signed certificate in certificate chain
```

`SELF_SIGNED_CERT_IN_CHAIN`은 방화벽·DNS 문제가 아니라 **TLS(HTTPS) 인증서 신뢰 문제**입니다.
회사·기관 네트워크의 보안 장비나 PC에 설치된 백신/보안 소프트웨어가 "TLS 검사(SSL
inspection)"라는 방식으로 HTTPS 트래픽을 중간에서 가로채 자체 서명 인증서로 다시
서명하는 경우가 흔한 원인입니다(합법적인 보안 목적으로 흔히 쓰이는 방식입니다). 브라우저는
이 인증서를 OS/브라우저 인증서 저장소에 이미 등록해 신뢰하도록 설정돼 있는 경우가 많지만,
Node.js는 이 저장소를 따로 참조하지 않고 자체 CA 목록만 신뢰하기 때문에 브라우저에서는
멀쩡히 열리는 `data.go.kr` 사이트가 Node의 `fetch`에서는 거부되는 것입니다.

가장 안전한 해결책은 그 보안 소프트웨어/네트워크 장비의 루트 인증서를 Node에 직접
신뢰시키는 것입니다: 브라우저(Chrome 기준 설정 > 개인정보 및 보안 > 보안 > 인증서 관리)에서
`apis.data.go.kr` 접속에 쓰이는 루트 인증서를 `.pem` 형식으로 내보낸 뒤, 앱 실행 시
`NODE_EXTRA_CA_CERTS=/경로/내보낸인증서.pem npm run dev`처럼 환경변수로 지정하면 Node가
그 인증서를 신뢰하게 되어 정상적으로 검증까지 통과합니다. 다만 이 인증서를 찾아 내보내는
과정이 번거로울 수 있어서, 더 간단한 우회 옵션도 함께 추가했습니다: `.env.local`에
`MOLIT_ALLOW_INSECURE_TLS=1`을 설정하면 **국토부 API 요청에 한해서만** 인증서 검증을
건너뜁니다(앱의 다른 기능이나 Node 프로세스 전체에는 영향을 주지 않습니다). 구현은
`lib/molit.js`에서 이 플래그가 켜졌을 때만 `undici` 패키지의 `fetch`를
`Agent({ connect: { rejectUnauthorized: false } })` 디스패처와 함께 쓰도록 했고, 꺼져 있으면
기존과 동일하게 Node 기본 `fetch`를 그대로 씁니다.

**주의**: 이 우회 옵션을 켜면 국토부 API로 가는 트래픽이 중간에서 조작되어도 앱이 알아챌
방법이 없어집니다. 회사·기관 네트워크나 신뢰하는 PC의 보안 소프트웨어 때문이라면(가장 흔한
경우) 위험은 낮지만, 신뢰할 수 없는 네트워크(카페·공항 등 공용 와이파이)에서는 켜지 않는
것을 권장합니다.

검증은 자체 서명 인증서를 쓰는 로컬 HTTPS 테스트 서버를 직접 띄워서, `lib/molit.js`의 실제
호출 경로(`fetchAvgPricePerPyeong` → `callApi` → `throttledMolitFetch`)를 그대로 태워
(1) `MOLIT_ALLOW_INSECURE_TLS`가 꺼져 있을 때는 지금처럼 자체 서명 인증서를 거부하는지
(보안이 기본적으로 유지되는지), (2) `1`로 켜면 같은 서버에서 실제로 데이터를 정상적으로
받아와 파싱까지 되는지 둘 다 확인했습니다. 11~13장 회귀 테스트도 다시 돌려 콘솔 에러 없이
통과하는 것을 확인했습니다.

## 14. 매물 후보를 구당 4건만 보여주던 것을 "더보기"로 더 볼 수 있게 개선

TLS 문제를 해결하고 실제 매물이 뜨자, 사용자가 서버 로그에는 구 하나당 실거래가 수십~수백
건씩(예: 로그의 `파싱된 유효 거래=123건`) 잡히는데 화면에는 구당 딱 4개만 보이는 걸 보고
"더 많이 보여줄 수 있을 것 같다"고 알려줬습니다. 확인해보니 `lib/candidates.js`의
`findCandidates`가 화면에 보여줄 개수를 `limit`(기본값 4)으로 딱 잘라내고 있었고,
`app/api/recommend/route.js`는 이 값을 넘겨주지 않아 항상 기본값 4가 쓰이고 있었습니다 —
서버가 이미 조회해서 걸러낸 매물이 훨씬 많은데 화면에서 스스로 4개로 줄이고 있었던
것입니다.

- `route.js`의 `CANDIDATE_LIMIT_PER_DISTRICT`를 처음엔 20으로 올렸다가, 사용자가 "더보기를
  누를 때마다 건수를 늘리면 되지 않냐"고 다시 피드백을 줘서 아예 `Infinity`로 바꿨습니다 —
  이제 인위적인 상한 없이, `findCandidates`가 최근 2개월치 실거래를 조회·중복제거한 만큼
  전부 API 응답에 담아 화면까지 전달합니다(실질적인 한도는 국토부 API 자체의 페이지당
  조회 건수뿐입니다).
- `RankFlow.js`의 `CandidateList`는 처음엔 4건만 보여주고(기존과 동일한 첫인상 유지), 제목
  옆에 "· 총 N건"으로 실제 받아온 개수를 표시합니다. "매물 8건 더보기 (남은 M건)" 버튼을
  누를 때마다 8건씩 더 펼쳐지고(마지막 페이지는 남은 만큼만), 다 펼치면 버튼이 "접기"로
  바뀌어 다시 4건으로 되돌릴 수 있습니다 — 추가 API 호출 없이 이미 받아온 데이터 안에서
  펼치므로 클릭할 때마다 즉시 반응합니다.

이 UI를 검증하려면 실제 매물 데이터가 있어야 하는데(개발 환경은 국토부 API에 못 나갑니다),
`callApi`에 §4처럼 임시 QA 모킹 훅을 잠깐 추가해 한 지역에서 중복제거 후 30건이 나오도록
만든 뒤 Playwright로 (1) 기본 상태에서 정확히 4건만 보이는지, (2) "더보기"를 4번 눌러
4→12→20→28→30건으로 정확히 8건씩(마지막엔 남은 2건만) 늘어나며 버튼 문구의 "남은 N건"도
매번 정확히 줄어드는지, (3) 다 펼친 뒤 "접기"를 누르면 정확히 4건으로 되돌아가는지 확인한
뒤, 검증이 끝나자마자 훅을 다시 제거했습니다(`grep -n "QA_MOCK_MOLIT" lib/molit.js`로
흔적이 없는 것까지 확인). 11~13장 회귀 테스트도 다시 돌려 콘솔 에러 없이 통과하는 것을
확인했습니다.

## 15. "중구·마포구·영등포구·성동구 등 데이터가 없는 곳도 잘 체크해봐" — 확인 결과: 버그 아님, 그런데 표시가 오해를 살 수 있어서 개선

사용자가 서울특별시로 시/도 검색을 해보고 마포구·성동구 같은 실제로는 거래가 활발한 구가
"매물 후보" 섹션 자체가 안 보이는 것을 발견해서, 이게 진짜 데이터 문제인지 확인해 달라고
요청했습니다.

먼저 `lib/districts.js`의 법정동코드부터 확인했습니다 — 혹시 중구/마포구/영등포구/성동구의
`lawdCd`가 잘못 매핑돼 있어서 엉뚱한 지역을 조회하고 있는 게 아닌지 의심했지만, 4곳 모두
공식 법정동코드(중구 11140, 성동구 11200, 마포구 11440, 영등포구 11560)와 정확히 일치했고
문제가 없었습니다.

진짜 원인은 다른 곳에 있었습니다. `app/api/recommend/route.js`는 API 호출을 아끼기 위해
점수 랭킹 상위 `CANDIDATE_DISTRICT_COUNT`(5)개 지역에 대해서만 실제 매물 후보를 조회하고,
나머지 지역은 애초에 조회 자체를 하지 않습니다. 화면 코드(`RankFlow.js`)는 이 "조회 안 함"
상태를 조용히 아무것도 안 그리는 것으로만 처리하고 있어서, 사용자 입장에서는 "이 지역만
매물 정보가 빠졌나?"로 오해하기 딱 좋은 모양이었습니다. 실제로 서울특별시 전체(25개 구)를
시/도 검색으로 테스트해보니 마포구는 6위, 성동구는 9위, 동작구는 10위로 나왔고(가중치·검색
중심점에 따라 순위는 바뀔 수 있습니다), 상위 5위 안에 들지 못해 매물 후보 조회 대상에서
빠진 것이었습니다 — 즉 버그가 아니라 의도된 동작이지만, 그 이유를 화면에서 전혀 설명하지
않은 게 문제였습니다.

그래서 `ResultCard`에 순위(`rank`)와 `candidateDistrictCount`, `liveEnabled`를 함께
넘겨서, "이 지역은 순위가 상위 N위 밖이라 아직 조회하지 않았다"는 것을 명확한 안내
문구로 보여주도록 고쳤습니다. 이제 세 가지 상태가 화면에서 뚜렷하게 구분됩니다:

- 상위 N개 지역이면서 매물이 실제로 있으면 → 매물 후보 목록이 그대로 보입니다.
- 상위 N개 지역인데 조회 자체가 실패했으면 → (13장에서 만든) "일부 지역의 매물 후보를
  불러오지 못했습니다" 에러 박스에 원인과 함께 뜹니다.
- 상위 N개 밖이라 아예 조회하지 않은 지역이면 → "실거래 API 호출을 아끼기 위해 점수 순위
  상위 N개 지역만 매물 후보를 조회합니다(현재 M위) — 데이터가 없는 게 아니라 아직 조회하지
  않은 지역입니다"라는 문구가 뜨고, 가중치를 조절하거나 반경/시·도 범위를 좁혀서 순위를
  올리면 확인할 수 있다는 안내까지 함께 보여줍니다.

검증은 가짜(무효) 서비스키로 실제 국토부 API 호출이 전부 403으로 실패하는 상태를 만들어
(1) 상위 5개 지역은 카드마다 별도 안내 없이 상단 에러 박스에만 원인이 모이는지, (2) 6~10위
지역은 정확히 새 안내 문구("아직 조회하지 않은")가 뜨는지, (3) `/api/recommend` 응답에서
실제로 마포구·성동구·동작구가 상위 5위 밖으로 나오는지를 curl과 Playwright로 함께
확인했습니다(가짜 키라 진짜 매물 데이터로 최종 확인하진 못했지만, 이 부분은 데이터 유무와
무관하게 순위·조회 로직만으로 결정되는 화면 문제였으므로 이 정도 검증으로 충분하다고
판단했습니다). 11~14장 회귀 테스트도 다시 돌려 콘솔 에러 없이 통과하는 것을 확인했습니다.

### 15-1. "랭킹 상관없이 모두 조회해" — 상위 5개 제한 자체를 없앰

바로 위 15장에서 "상위 5개만 조회하고 나머지는 안내 문구로 설명한다"로 마무리했는데,
사용자가 그 대신 "화면에 보이는 지역이면 순위와 상관없이 다 조회해달라"고 다시 요청했습니다.
API 호출을 아끼려던 원래 취지보다 사용자가 원하는 게 명확했으므로, 상위 5개라는 제한
자체를 없앴습니다.

- `route.js`의 `CANDIDATE_DISTRICT_COUNT`를 5 → 10으로 바꿨습니다. 이 값은 `RankFlow.js`가
  실제로 카드를 그리는 개수(`top10 = data.results.slice(0, 10)`)와 정확히 같아야
  "화면엔 보이는데 조회는 안 된 지역"이 다시 생기지 않으므로, 두 파일 모두에 서로를
  참조하는 동기화 주석을 남겼습니다.
- 그 결과 15장에서 추가했던 "아직 조회하지 않은 지역" 안내 문구는 이제 화면에 보이는 10개
  지역에 대해서는 뜰 일이 없어집니다(순위 10위 밖, 즉 애초에 카드 자체가 안 그려지는
  지역에서만 이론적으로 유효한 코드로 남아 있습니다 — 나중에 표시 개수나 조회 개수 둘 중
  하나만 바꾸는 실수를 하면 다시 나타날 수 있으니 그대로 남겨 뒀습니다).
- 반경/시·도 검색으로 좁힌 지역 풀(`poolDistricts`)이 몇십~몇백 개여도 실제 매물 후보
  조회는 항상 화면에 보이는 10개로만 유지되므로, 검색 범위를 넓게 잡아도 API 호출량이
  갑자기 폭증하지는 않습니다(평균가 조회는 원래도 풀 전체에 대해 이루어지고, 이번 변경은
  매물 후보 조회 대상만 5→10으로 늘린 것입니다).

검증은 가짜 서비스키로 서울특별시 시/도 검색을 돌려서 (1) API 응답의 `candidatesByDistrict`
에 상위 10개 지역(마포구·성동구·동작구 포함) 전부가 키로 들어있는지 curl로, (2) 화면에서
10개 카드 전부 "아직 조회하지 않은" 안내가 더 이상 뜨지 않고 상단 에러 박스로만 원인이
모이는지 Playwright로 확인했습니다. 11~14장 회귀 테스트도 다시 돌려 콘솔 에러 없이
통과하는 것을 확인했습니다.

## 16. ① 모드 지도/매물 UX 대폭 개선 (7가지 요청 반영)

사용자가 ①모드("어디로 갈지 추천받기")에 대해 한 번에 7가지를 요청했습니다:

1. 추천받기를 누르면 지도가 포커싱되고, 지도 위에 실제 매물 후보가 표시됐으면 좋겠다.
2. 매물이 지도에 꽂힐 때 애니메이션/음향 효과가 있었으면 좋겠다.
3. 매물 목록을 가격 낮은 순으로 보여달라.
4. 가격이 눈에 확 띄게 색을 입혀달라.
5. "내 위치 사용"을 지도 위에 "+" 버튼으로 표시해달라.
6. 직장 위치 빠른 선택(서울 한정)은 없어도 된다.
7. 지도에 지하철역을 표시해주면 좋겠다.

하나씩 어떻게 반영했는지, 그리고 왜 그렇게 설계했는지 정리합니다.

### 16-1. 매물 후보 지도 핀 + 다트 애니메이션/사운드 (1, 2번)

②모드(지역 우선, `DistrictFlow.js`)는 이미 실제 매물 좌표를 지도에 "다트가 꽂히는"
연출로 보여주고 있었습니다. ①모드는 지역 랭킹 점수 색상 점만 찍고 있었는데, 같은 방식을
①모드 결과 지도에도 적용했습니다.

가장 큰 문제는 **속도**였습니다. 매물의 정확한 좌표는 국토부 API가 주지 않아서(법정동+
단지명 텍스트뿐) `lib/geocode.js`가 OpenStreetMap Nominatim으로 지오코딩을 하는데,
Nominatim 정책상 초당 1건까지만 요청할 수 있습니다. ①모드는 한 번에 최대 10개 지역의
매물을 보여주므로, 지역마다 몇 건씩만 지오코딩해도 실시간으로 하면 추천 결과 자체가
10초 이상 늦게 뜨게 됩니다.

그래서 **지오코딩을 추천 결과 API(`/api/recommend`)에서 분리**했습니다:

- `/api/recommend`는 예전처럼 즉시 응답합니다(랭킹, 예산 점수, 매물 목록 전부 그대로).
- 화면에 결과가 뜨자마자, 새로 만든 `/api/candidate-coords`로 상위 10개 지역 × 지역당
  최대 5건(가격 낮은 순 상위 5건)의 좌표를 별도로 요청합니다. 이 요청 전체에 실제
  Nominatim 조회 총 20건이라는 상한을 둬서(나머지는 지역 중심 근처에 흩뿌려 표시),
  아무리 지역이 많아도 이 조회가 20초 이상 걸리지 않게 막았습니다.
- 좌표가 도착하면 그 순간 지도에 매물 핀이 다트처럼 "파팍" 소리와 함께 순서대로
  꽂히는 연출이 재생됩니다(②모드와 같은 `dartMarker.js`/`dartAudio.js`를 그대로
  재사용). 예산 이내(초록)/초과(주황)/모름(회색)로 색을 구분합니다.
- "추천받기"를 누른 그 순간에는 지도가 결과 중심으로 부드럽게(`flyTo`) 포커싱되는
  연출이 먼저 재생되고(1번 요청의 "지도로 포커싱"), 매물 핀은 그 뒤 좌표가 준비되는
  대로 이어서 꽂힙니다.
- `lib/geocode.js`가 지금까지 검색어에 "서울특별시"를 하드코딩하고 있던 버그도 함께
  고쳤습니다(①모드가 전국 검색을 지원하면서 드러났습니다 — 서울 밖 지역은 애초에
  검색어 자체가 틀려서 지오코딩이 항상 실패하고 있었습니다). 이제 실제 시/도 이름을
  넘겨받아 씁니다. ②모드도 같은 함수를 쓰므로 이 버그 수정의 혜택을 함께 받습니다.
- Nominatim 요청에 타임아웃(8초)이 없어서, 만약 응답이 아예 멈춰버리면 뒤에 대기 중인
  모든 지오코딩 요청까지 함께 멈추는 잠재적 문제도 발견해서 같이 고쳤습니다.

### 16-2. 매물 가격 낮은 순 정렬 (3번)

`lib/candidates.js`의 `findCandidates()`가 예전엔 최근 거래월 순으로 정렬했는데, 총액
(전세/월세는 보증금 총액) 오름차순으로 바꿨습니다. 지도 핀도 이미 정렬된 목록의 상위
몇 건을 그대로 쓰므로, 자연스럽게 "가장 저렴한 매물부터" 지도에도 찍힙니다.

### 16-3. 가격 강조 색상 (4번)

매물 카드의 가격 텍스트를 굵게 + 포인트 컬러(진한 핑크빛 레드, 다크모드에서는 더 밝은
톤)로 바꿔서 한눈에 들어오게 했습니다. ①모드·②모드 둘 다 같은 스타일을 적용했습니다.

### 16-4. "내 위치 사용"을 지도 위 "+" 버튼으로 (5번)

지도 아래 별도 버튼으로 있던 "내 위치 사용"을 지도 오른쪽 위에 떠 있는 원형 "+" 버튼으로
옮겼습니다. 동작(현재 위치로 지도 중심 이동)은 그대로입니다.

### 16-5. 직장 빠른 선택 칩 제거 (6번)

서울 지역 몇 곳만 있던 빠른 선택 칩(강남역, 판교테크노밸리 등)을 지웠습니다. `lib/workplaces.js`
파일 자체와 ②모드에서 쓰는 하위 호환 경로는 그대로 뒀습니다(다른 곳에서도 참조하고
있어서 지우면 오히려 위험하고, 화면에 노출되지 않으면 사용자 요청은 충족됩니다).

### 16-6. 지도 위 지하철역 표시 (7번)

국토부 API에는 지하철역 정보가 없어서, OpenStreetMap의 무료 Overpass API로 지도 중심
근처의 지하철/경전철역을 조회하는 `lib/subway.js`와 `/api/subway` 엔드포인트를
새로 만들었습니다. 위치 선택 지도와 결과 지도 양쪽 모두에 보라색 작은 점으로 표시됩니다.

- 추천 결과와는 무관한 "곁들이는" 정보라, 조회가 느리거나 실패해도 추천 결과 자체에는
  전혀 영향이 없도록 완전히 별도 요청으로 분리했습니다.
- Overpass도 공용 서버라 응답이 느리거나 실패할 수 있어(타임아웃 9초), 실패 시 조용히
  빈 배열로 폴백하고 지도에는 그냥 표시되지 않습니다.
- 같은 위치를 반복 조회하지 않도록 서버 메모리에 30분간 캐시합니다.
- 결과 지도는 화면에 표시된 지역들이 퍼진 범위에 맞춰 조회 반경을 자동으로 조절합니다
  (최대 25km로 제한 — 너무 넓으면 응답이 느려지고 점도 지나치게 많아집니다).

### 검증

가짜 서비스키 + mock 실거래 데이터로 ①모드에서 시/도(서울특별시) 검색을 돌려
Playwright로 확인했습니다:

- 직장 프리셋 칩(`chip-row`/`locate-chip`)이 화면에서 완전히 사라졌는지
- 지도 위 "+" 버튼이 있고 클릭 시 에러 없이 동작하는지
- 결과 카드 10개 각각의 매물 목록이 가격 오름차순인지
- 가격 텍스트가 굵게 + 포인트 컬러로 렌더링되는지 (`getComputedStyle`로 실제 색상 확인)
- `/api/candidate-coords` 응답이 도착한 뒤 결과 지도에 다트 핀(구 중심 1개 + 매물 후보
  최대 50개)이 실제로 늘어나는지
- 이 샌드박스 환경은 외부 네트워크(Nominatim/Overpass)가 막혀 있어 실제 지오코딩/지하철
  조회 자체는 검증할 수 없었지만, `/api/candidate-coords`와 `/api/subway`를 직접
  호출해 네트워크 실패 시에도 200 응답 + 안전한 폴백(지역 중심 근처 흩뿌림 좌표 /
  빈 배열)이 오는 것과 서버가 멈추지 않는 것을 확인했습니다. 실제 인터넷이 되는
  환경(사용자 PC)에서는 진짜 좌표/역 정보가 채워집니다.
- 기존 회귀 테스트(9~15장: 전국 확장, 예산 슬라이더, 매물 후보 진단 로그, 더보기
  페이지네이션, 랭킹과 무관한 전체 조회)도 다시 돌려 콘솔 에러 없이 통과하는 것을
  확인했습니다.

## 17. 지도 위 버튼을 아이콘형 위치/확대·축소 컨트롤로 교체 + 매물 핀 낙하 속도 개선

사용자가 두 가지를 요청했습니다: (1) 지도 위 "내 위치 사용" 버튼을 텍스트 "+"가 아니라
위치(⊙) 아이콘 버튼 + 그 아래 별도 확대/축소(+/−) 버튼으로 바꿔달라(참고 이미지 첨부),
(2) 매물 후보 핀이 지도에 꽂히는 애니메이션이 너무 느리니, 지오코딩으로 빠르게 할 수
있으면 그렇게 해달라.

### 17-1. 버튼 디자인 교체

- "내 위치 사용" 버튼의 텍스트 "+"를 위치 아이콘(가운데 점 + 십자 크로스헤어) SVG로
  바꿨습니다.
- 리플렛 지도의 기본 확대/축소 컨트롤은 원래 왼쪽 위에 있었는데, 이제 `LeafletMap.js`에서
  `map.zoomControl.setPosition("topright")`로 오른쪽 위로 옮기고, 위의 위치 버튼과 겹치지
  않도록 그 아래로 내린 뒤(`globals.css`의 `.leaflet-top.leaflet-right` margin-top), 흰
  배경 + 둥근 모서리로 다시 꾸며서 위치 버튼과 톤을 맞췄습니다.

### 17-2. 매물 핀 낙하 속도 개선

느렸던 진짜 이유를 확인해 보니 두 가지였습니다:

1. **먹통 구간이 길었음**: 이전엔 `/api/candidate-coords`가 상위 10개 지역을 전부 조회
   (지역당 최대 5건, 실제 Nominatim 지오코딩은 요청 전체에 20건까지 허용)한 뒤에야
   응답 하나로 한꺼번에 돌려줬습니다. Nominatim이 초당 1건 제한이라 이 조회 자체가
   최대 20초 넘게 걸릴 수 있었고, 그동안 지도에는 아무 변화가 없었습니다.
2. **다 도착한 뒤엔 애니메이션도 길었음**: 응답이 오면 최대 50개 핀이 한 번에 순서대로
   "파팍" 떨어지는 연출이 재생되는데, 핀 하나당 딜레이가 있어 이것만 6초 넘게 걸렸습니다.

그래서 사용자가 물어본 대로 "지오코딩을 빠르게" 했습니다:

- **스트리밍으로 전환**: `/api/candidate-coords`를 한 번에 응답하는 대신, 지역 하나가
  끝나는 대로 그 지역 결과만 즉시 한 줄(NDJSON)로 흘려보내도록 바꿨습니다(Next.js
  `ReadableStream`). 화면에서는 지역이 도착하는 대로 그때그때 좌표를 반영하고 핀을
  꽂습니다 — 이제 첫 지역은 거의 즉시 뜨고, 나머지는 이어서 하나씩 나타납니다.
- **구당 지도 핀 개수를 5→3건으로 축소**: 지도에는 어차피 카드보다 적은 수만 참고용으로
  보여주면 되므로, 저렴한 순 상위 3건만 지오코딩합니다.
- **실제 지오코딩 총 한도를 20→10건으로 축소**: 전체 요청에서 진짜 Nominatim 조회는
  최대 10건까지만 시도하고, 그 이상은 지역 중심 근처에 흩뿌려 표시합니다(정확도보다
  체감 속도를 우선한 트레이드오프입니다 — 흩뿌려진 핀은 "정확한 위치 아님"으로 표시됩니다).
- **핀이 중복으로 다시 떨어지지 않게 처리**: 지역별로 나눠서 도착하다 보니, 그냥 두면
  새 지역이 도착할 때마다 이미 꽂혀 있던 이전 지역 핀들까지 매번 다시 "파팍" 떨어지는
  것처럼 보이는 문제가 생깁니다. `LeafletMap.js`에 마커별 `settled` 플래그를 추가해서,
  가장 최근에 도착한 지역의 핀만 이번에 낙하 애니메이션을 재생하고 이미 꽂혀 있던 핀은
  다트 모양은 유지한 채 조용히 그대로 있게 했습니다.
- 참고로 Nominatim 요청 자체에 타임아웃이 없어서, 만약 응답이 멈춰버리면 뒤에 대기
  중인 모든 요청까지 함께 멈추는 잠재적 문제도 지난 라운드(16장)에서 이미 고쳐뒀습니다.

### 검증

Playwright로 확인했습니다:

- 위치 버튼이 SVG 아이콘을 쓰는지, 확대/축소 컨트롤이 오른쪽 위 위치 버튼 바로 아래에
  자리 잡는지(좌표로 직접 비교)
- `curl --raw`로 `/api/candidate-coords` 응답이 실제로 청크 단위(chunked transfer)로
  끊어서 전송되는지 — 지역별로 별도 줄이 순서대로 도착하는 것을 확인
- 지도 핀이 10개 지역 × 3건 + 원점 마커 1개 = 최대 31개로 줄었는지, 그리고 결과가 뜨는
  시점부터 첫 매물 핀이 나타나는 시점까지 걸리는 시간을 측정
- 콘솔 에러 없이 전 과정이 진행되는지
- 이 샌드박스는 외부 네트워크가 막혀 있어 Nominatim 응답이 실패로 아주 빨리 끝나버리는
  환경이라, 실제 사용자 네트워크(1건당 ~1.1초)에서 체감되는 개선 폭을 그대로 재현할 수는
  없었습니다. 다만 `curl --raw`로 스트리밍 자체가 정상 작동하는 것과, `settled` 로직이
  똑같은 지역 핀을 중복으로 다시 떨어뜨리지 않는 것은 코드 레벨로 확인했습니다.

## 18. "강남구·마포구에 1건씩만 조회된다" — 실제 매물이 부당하게 숨겨지던 버그 발견/수정

사용자가 서울특별시에서 매매·오피스텔·5년 이내 신축·목표예산 5~17.5억·17평 이상 조건으로
검색했더니 강남구·마포구에 딱 1건씩만 나왔다며 "말이 안 되는 것 같다"고 신고했습니다.

이 샌드박스에서는 실제 국토부 API에 접속할 수 없어서, §4처럼 `lib/molit.js`의 `callApi`에
임시 mock을 넣어 "같은 오피스텔 단지, 같은 평형대(전용 62~63㎡), 하지만 서로 다른 층"인
실거래 8건을 심어 재현했습니다. 결과: 8건을 심었는데 화면엔 **2건만** 남았습니다(사용자가
겪은 것보다도 더 심했습니다 — 조건 조합에 따라 1건이 될 수도 있다는 뜻입니다).

### 원인

`lib/candidates.js`의 `dedupeLatest()`가 "단지명 + 반올림한 전용면적"만으로 매물을
묶어서 그중 최신 거래만 남기고 있었습니다. 원래는 같은 매물이 API 응답에 두 번 잡히는
것을 막으려는 의도였을 텐데, **층 정보를 묶음 기준에서 빼먹어서** 실제로는 서로 다른
호실(다른 층)인 매물들까지 "같은 매물"로 취급해 하나로 합쳐버리고 있었습니다.

오피스텔은 건물 전체가 몇 가지 표준 평형(전용면적)으로만 지어지는 경우가 많아서, 같은
단지에서 여러 호실이 거래돼도 전용면적은 거의 같습니다 — 그래서 이 버그가 유독 오피스텔
조건에서(그리고 표준화된 평면이 많은 대단지 아파트에서도) 두드러지게 나타납니다. 강남구
같은 곳은 실제로는 조건에 맞는 거래가 여러 건 있었을 가능성이 높은데, 화면엔 그중 우연히
맵(Map) 순회 순서상 먼저 걸린 1건만 남고 나머지는 조용히 사라지고 있었습니다.

### 수정

`dedupeLatest()`의 묶음 기준(key)에 `floor`(층)를 추가했습니다: `단지명::반올림면적::층`.
이제 같은 단지·같은 평형이라도 층이 다르면 서로 다른 매물로 취급해 전부 보여주고, 정말
같은 호실이 기간 안에 두 번 거래된 경우(단지+면적+층까지 전부 같음)에만 최신 거래로
합칩니다.

### 검증

같은 mock(같은 단지, 같은 평형대, 층만 다른 8건)으로 수정 전/후를 비교했습니다:

- 수정 전: 서울 상위 10개 지역 전부 2건씩만 표시(8건 중 6건이 부당하게 사라짐)
- 수정 후: 10개 지역 전부 8건씩 정상 표시, 가격 오름차순 정렬도 그대로 유지됨을 확인

기존 회귀 테스트(더보기 페이지네이션, 가격 정렬·색상, 지도 핀 스트리밍, 위치/확대축소
버튼)도 다시 돌려 이번 수정으로 다른 기능이 깨지지 않았는지 확인했습니다 — 페이지네이션
테스트에 쓰던 mock은 단지명·층이 항목마다 전부 달라서 원래도 이 버그의 영향을 받지 않는
데이터였고, 수정 후에도 동일하게 6건이 유지되는 것으로 재확인했습니다.

이 버그는 ②모드(지역 우선, `DistrictFlow.js`)와 예산 자동계산(`computePriceRange`,
dedupe를 쓰지 않음)에는 영향이 없었고, ①모드의 "실제 매물 후보" 목록에만 영향이
있었습니다.

## 19. ① 모드 결과 카드에서 의미 없는 순위·점수·막대그래프·세부 참고지수 제거

사용자가 결과 카드 화면을 보고 "표시된 정보 중에 예상시세, 예상 총액 이외의 정보는 의미가
없다. 그래프도 의미 없다"며 제거를 요청했습니다. 카드 맨 위의 순위(#1)·총점(85.6점)
배지는 요청 문구에 직접 언급되진 않았지만 애매해서, 함께 지울지 확인 질문을 드렸고
"순위·총점도 함께 제거"로 답을 받아 아래처럼 정리했습니다.

### 제거한 것 (`app/components/RankFlow.js`의 `ResultCard`)

- 카드 맨 위 순위 배지(`#1` 등)와 총점 배지(`85.6점` 등)
- 예산/통근/학군/치안·편의 막대그래프(가로 바 4줄)
- 세부 참고지수 3종: 예상 통근시간, 학군 참고지수, 치안·편의 참고지수

### 남긴 것

- 지역명(시/도 + 구/군)
- 예상 시세(평당) — 실거래가 실시간 조회인지 조사 참고값인지 안내 문구 포함
- 예상 총액

지도 아래 있던 범례(`.legend`, 예산/통근/학군/치안 색상 안내)도 막대그래프를 설명하기
위한 것이었는데 막대그래프 자체가 없어져 더는 화면에 대응하는 요소가 없어졌으므로 함께
지웠습니다. 다만 카드 위 입력 단계인 "3. 무엇을 가장 중요하게 볼까요?"의 가중치 슬라이더는
이번 요청과 무관한 별개 기능(사용자가 점수 계산 비중을 직접 조절하는 입력)이라 그대로
남겨뒀습니다.

정렬 자체는 그대로 점수(총점) 기준으로 매깁니다 — 화면에 숫자로 보여주지만 않을 뿐이며,
카드가 나열되는 순서(가장 적합한 지역이 위로)에는 영향이 없습니다.

`globals.css`에서도 더 이상 쓰이지 않는 `.legend`, `.result-head .rank`,
`.result-head .total`, `.bars`, `.bar-row`, `.bar-track`, `.bar-fill` 관련 스타일을
함께 정리했습니다.

### 검증

`fetchRecentListings`에 임시 mock을 넣어 서울 상위 10개 지역 결과 카드를 렌더링한 뒤
확인했습니다: 순위/총점 배지 0개, 막대그래프 요소 0개, 범례 0개, 각 카드의 상세 블록은
정확히 2개(예상 시세·예상 총액)만 남음, 카드 안 어디에도 "N점" 형태 텍스트 없음. 기존
회귀 테스트(더보기 페이지네이션, 가격 정렬·색상, 지도 핀 스트리밍, 위치/확대축소 버튼,
직장 칩 제거)도 다시 돌려 콘솔 에러 없이 정상 동작함을 재확인했습니다.

## 20. "시/도로 찾기" 탭의 지도를 시/도 경계가 표시되는 전국 전도로 교체(드롭다운 대신 클릭으로 선택)

사용자가 "시/도로 찾기"로 탭을 옮기면 위에 있던 지도(반경 모드용 확대 지도)가 그대로
남아 있고 시/도는 별도의 드롭다운으로만 고르게 되어 있던 것을, "지도가 전국 전도로
바뀌면서 시/도별 경계를 표시하고, 그 지도에서 바로 클릭해 고를 수 있게" 해 달라고
요청했습니다. 텍스트 입력(드롭다운)과 지도의 위/아래 순서는 필요하면 바꿔도 된다고
허용해 주셨습니다.

### 구현

- **경계 데이터**: 통계청 행정구역 경계(2018년 시/도 기준, `southkorea/southkorea-maps`
  공개 데이터)를 내려받아 `mapshaper`로 단순화(약 7.5MB → 188KB)했습니다. 2023~2024년
  개편으로 이름이 바뀐 강원도→강원특별자치도, 전라북도→전북특별자치도는 앱에서 쓰는
  최신 명칭으로 맞춰뒀습니다(17개 시/도 이름이 `lib/districts.js`의 시/도 목록과 정확히
  일치하는 것을 확인했습니다). 파일은 `public/geo/skorea-sido.json`에 두고, "시/도로
  찾기" 탭을 처음 켤 때만 지연 로딩합니다(반경 모드만 쓰는 사람에게 굳이 내려받게
  하지 않기 위해서입니다).
- **지도 컴포넌트(`LeafletMap.js`)**: `sidoBoundaries={data, selectedName, onSelect}`
  prop을 새로 받아 Leaflet의 `L.geoJSON`으로 경계를 그립니다. 선택된 시/도는 진하게
  칠하고, 나머지는 옅게 표시하며, 마우스를 올리면 이름 툴팁과 함께 살짝 강조됩니다.
  시/도 영역을 클릭하면 `onSelect(name, {lat, lng})`를 호출합니다.
- **화면 흐름(`RankFlow.js`)**: "시/도로 찾기" 탭을 선택하면 지도가 검색 중심점 확대
  화면 대신 전국이 한눈에 들어오는 고정 시점(위도 36.3, 확대 7)으로 바뀌고, 반경 원
  대신 시/도 경계가 표시됩니다. 시/도 영역을 클릭하면 그 시/도가 선택되면서(드롭다운도
  같이 갱신됨), **클릭한 정확한 좌표가 통근시간 계산 기준점(origin)으로도 함께
  저장됩니다** — 이 앱은 "시/도로 찾기" 모드에서도 통근시간 점수를 계산할 기준 위치가
  필요한데(3번 가중치 슬라이더의 "통근시간" 항목), 지도 클릭 한 번으로 지역 선택과
  기준점 지정을 동시에 처리하게 했습니다. 드롭다운은 접근성과 정밀 선택(세종·대전처럼
  화면에서 작아 클릭하기 어려운 시/도)을 위해 그대로 남겨뒀고, 둘 다 같은 상태를
  가리키므로 어느 쪽으로 골라도 서로 반영됩니다. 반경 모드로 돌아가면 원래의
  확대 지도(내 위치 버튼, 반경 원)로 다시 바뀝니다.
- **레이아웃 순서 조정**: 탭(반경으로 찾기/시/도로 찾기)을 지도보다 위로 옮겨서, 먼저
  모드를 고르면 그에 맞는 지도가 바로 나오도록 흐름을 바꿨습니다. 안내 문구도 모드에
  따라 다르게 보여줍니다.

### 알아두면 좋은 점

- 리플렛 벡터 레이어(경계 폴리곤)는 클릭 이벤트가 기본적으로 지도 자체의 클릭까지
  같이 전파됩니다. 이걸 막지 않으면 시/도를 클릭해 정한 기준점 라벨("OO 안에서 클릭한
  위치")이 지도 클릭 핸들러에 의해 곧바로 "선택한 위치"라는 일반 라벨로 덮어써지는
  문제가 있었습니다 — 폴리곤 클릭 핸들러에서 `L.DomEvent.stopPropagation`으로 전파를
  막아 해결했습니다.
- 경계 데이터는 단순화 과정에서 아주 작은 섬 등 일부 디테일이 생략될 수 있지만,
  시/도를 구분해 클릭하는 용도로는 충분한 정확도입니다.

### 검증

Playwright로 확인했습니다: 시/도 탭 전환 시 경계 폴리곤 17개가 모두 렌더링됨, 지도의
폴리곤을 클릭하면 드롭다운 선택값이 함께 바뀌고 현재 검색 중심점 라벨이 "OO 안에서
클릭한 위치"로 정확히 표시됨(전파 버그 수정 전에는 일반 라벨로 덮어써졌던 것을 재현
후 수정 확인), 드롭다운으로 골라도 지도의 강조 색이 즉시 따라 바뀜, 반경 모드로
되돌아가면 경계 폴리곤이 모두 사라지고 반경 원만 남음, 지도 클릭으로 고른 시/도 그대로
검색을 제출하면 결과의 지역 안내 문구에 그 시/도 이름이 정확히 반영됨. 기존 회귀
테스트(더보기 페이지네이션, 가격 정렬·색상, 지도 핀 스트리밍, 위치/확대축소 버튼,
결과 카드 단순화)도 다시 돌려 콘솔 에러 없이 정상 동작함을 재확인했습니다.

## 21. 탭 전환 시 현위치 자동 포커싱 + 지하철역 API 안정화 + 내 위치 버튼 지연 개선 + 설명문 축약

사용자가 네 가지를 한 번에 요청했습니다: (1) 반경/시·도 탭을 클릭하면 지도가 현위치로
자동 포커싱되게 해달라, (2) 지하철역 표시 기능이 실제로는 서버 로그에 `[subway] 지하철역
조회 실패 ... fetch failed`가 계속 찍히며 동작하지 않고 있다, (3) "내 위치 사용" 버튼을
누르면 바로 이동하지 않고 지연(delay)이 있다, (4) 화면 곳곳의 설명 문구가 너무 길다.

### 21-1. 탭 클릭 시 현위치 자동 포커싱

`RankFlow.js`에 `selectSearchMode(mode)`를 새로 만들어 탭 버튼에 연결했습니다. 다른
탭으로 전환하면: ① 일단 지금 알고 있는 위치로 즉시 한 번 포커싱하고, ② 동시에 위치를
다시 한번 확인해서(대부분 브라우저 캐시 덕분에 거의 즉시 반환됨 — 21-3 참고) 정확한
현위치로 다시 포커싱합니다. **이미 선택돼 있는 탭을 또 누른 경우는 아무 것도 하지
않습니다** — 지도를 클릭해 직접 고른 위치가 있는데 탭을 다시 눌렀다고 그 선택이
현위치로 되돌아가 버리면 오히려 불편하기 때문입니다(실제로 헷갈릴 수 있는 부분이라
Playwright로 "같은 탭 재클릭 시 직접 고른 위치가 보존되는지"까지 확인했습니다).

"시/도로 찾기" 지도의 기본 중심점도 손봤습니다: 예전엔 항상 고정된 좌표(전국이 딱 맞게
보이는 지점)만 썼는데, 이제 실제로 확인된 현위치가 있으면 그 위치를 중심으로 보여주고
(자동 포커싱), 아직 확인 전이면 기존처럼 전국이 고르게 보이는 좌표로 대신합니다. 다만
시/도 경계를 클릭해서 검색 기준점(origin)이 바뀌는 것과는 별개로 취급했습니다 — origin을
지도 중심 기준으로 그대로 썼다면 시/도를 클릭할 때마다 지도 시점이 그 지점으로 계속
끌려다니는 문제가 생기기 때문입니다.

### 21-2. 지하철역 API "fetch failed" 문제 진단/보강

로그의 `fetch failed`는 13-2장에서 국토부 API 호출이 겪었던 것과 정확히 같은 종류의
너무 뭉뚱그려진 에러 메시지입니다(진짜 원인은 `err.cause`에 있는데 로그에 남기지
않고 있었습니다). 같은 진단 방식을 공용 모듈로 뽑아 재사용했습니다:

- **`lib/netFetch.js`**(신규): `describeFetchError`로 `err.cause` 체인을 최대 3단계까지
  로그에 남기고(예: `SELF_SIGNED_CERT_IN_CHAIN`처럼 진짜 원인이 보이게), `netFetch`로
  국토부 API에 이미 있던 `MOLIT_ALLOW_INSECURE_TLS=1` 우회 옵션(13-2장 — 회사/기관
  네트워크의 TLS 검사로 인한 자체 서명 인증서 문제)을 **지하철역 Overpass API와
  지오코딩 Nominatim API 호출에도 동일하게 적용**했습니다. 이름은 국토부 API에서 처음
  발견돼 그대로 뒀지만, 실제로는 이 앱이 만드는 모든 외부 API 호출에 적용됩니다 — 같은
  네트워크에서 나가는 HTTPS 트래픽이라면 국토부 API만 막고 Overpass/Nominatim만 뚫려
  있을 이유가 없기 때문입니다.
- **Overpass 미러 서버 추가**(`lib/subway.js`): 공개 Overpass 서버 하나만 쓰면 트래픽이
  몰릴 때 응답을 거부하거나 느려지는 경우가 흔해서, `overpass-api.de` →
  `overpass.kumi.systems` → `overpass.openstreetmap.ru` 순서로 시도하도록
  바꿨습니다. 하나가 막혀 있어도 다음 미러로 자동으로 넘어가고, 셋 다 실패해야만
  기존처럼 빈 배열로 조용히 폴백합니다(지도의 다른 기능에는 영향 없음).
- 실패 로그도 `[subway] 지하철역 조회 실패(미러 3곳 모두 실패 ...)`처럼 시도한 미러별
  원인을 전부 남기도록 바꿔서, 만약 계속 실패하면 로그만 보고도 TLS 문제인지
  (`SELF_SIGNED_CERT_IN_CHAIN`이면 `MOLIT_ALLOW_INSECURE_TLS=1`로 해결) 다른 문제인지
  구분할 수 있게 했습니다.

이 샌드박스는 외부 네트워크가 막혀 있어 실제 Overpass 서버 접속까지는 확인할 수
없었지만(3개 미러 모두 순서대로 시도되고 각각의 실패 사유가 로그에 남는 것, 그리고
전부 실패해도 지도의 다른 기능에 영향이 없는 것은 확인했습니다), 회사·기관 네트워크의
TLS 검사가 원인이라면 국토부 API와 동일한 우회 옵션으로 해결될 가능성이 높습니다.

### 21-3. "내 위치 사용" 버튼 지연 개선

브라우저의 위치 확인 자체가 (특히 첫 요청일 때) 몇 초 걸리는 것은 브라우저 API의
본질적인 특성이라 완전히 없앨 수는 없지만, **반복 요청은 거의 즉시 끝나도록** 캐시를
활용하게 했습니다. `requestCurrentLocation({ maximumAge })` 공용 헬퍼를 새로 만들어
페이지 진입 시 조용히 확인한 위치, "내 위치" 버튼, 탭 전환 시 자동 포커싱이 전부 이
헬퍼를 함께 쓰도록 통일했습니다. `maximumAge: 60000`을 주면 60초 이내에 확인해 둔
위치가 있을 때 브라우저가 새로 몇 초씩 기다리지 않고 캐시에서 즉시 돌려줍니다 — 예를
들어 페이지가 열리자마자 조용히 위치를 한 번 확인해 두는데, 그 직후 사용자가 "내 위치"
버튼을 누르면 예전에는 또 처음부터 새로 확인하느라 몇 초가 걸렸지만 이제는 그 결과를
그대로 재사용해 즉시 반응합니다. Playwright로 가짜 위치를 주입해 확인해보니 버튼 클릭
후 완료까지 약 60~70ms로, 캐시가 확실히 동작하는 것을 확인했습니다.

### 21-4. 설명 문구 축약

지도/입력 단계 곳곳의 안내 문구가 3~4줄짜리 문단으로 길게 쓰여 있던 것을 핵심만 남기고
한두 줄로 줄였습니다(상단 소개 문구, 지도 위 안내, 방/화장실 안내, 결과 지도 범례 설명,
API 키 미설정 안내, 매물 미조회 지역 안내, 오류 안내 등). 정보 자체를 없애지 않고
"왜/어떻게"에 해당하는 부연 설명만 줄이고 핵심 사실(무엇을 할 수 있는지, 왜 이 상태인지)
은 그대로 남겼습니다.

### 검증

Playwright에 가짜 위치(부산시청 부근)를 주입해 확인했습니다: 페이지 진입 시 그 위치로
자동 포커싱됨, 반경↔시/도 탭을 오가도 현위치 기준이 유지됨, 지도를 직접 클릭해 다른
위치를 고른 뒤 같은 탭을 다시 눌러도 그 선택이 유지됨(자동 포커싱에 안 덮어써짐), 다른
탭으로 전환하면 현위치로 다시 스냅됨, "내 위치" 버튼 반복 클릭이 캐시로 수십 ms 만에
끝남. 지하철역 API는 미러 3곳이 순서대로 시도되고 실패 사유가 각각 로그에 남는 것을
확인했습니다. 기존 회귀 테스트(더보기 페이지네이션, 가격 정렬·색상, 결과 카드 단순화,
시/도 경계 지도)도 다시 돌려 콘솔 에러 없이 통과하는 것을 재확인했습니다.

## 22. 마이홈포털·청약홈·LH 공공주택 정보 연동("붙일 수 있는 건 다 붙여줘")

19번 장에서 답한 "실시간 정보를 알 수 있나?"라는 질문에 이어, 실제로 붙일 수 있는
공공데이터포털(data.go.kr) API를 조사해 붙였습니다. 다만 "붙일 수 있는 건 다"의 기준을
**필드명(응답 스키마)이 문서로 정확히 확인된 것만**으로 삼았습니다 — 13-2장에서 국토부
API 필드명을 잘못 짐작해 "단지명 미상"이 나오던 사고를 이미 겪었기 때문에, 같은 실수를
반복하지 않으려는 의도적인 선택입니다. data.go.kr의 일부 데이터셋은 정확한 필드명이
로그인 후에만 열리는 첨부파일(xlsx)에만 있어서, 이번 조사로는 그 내용을 확인할 수
없었습니다. 그런 데이터셋은 짐작으로 붙이지 않고 아예 제외했습니다.

### 22-1. 연동한 3개 API

- **LH 공공임대주택 단지정보 조회 서비스** (`lib/lhRental.js`, data.go.kr 15058476):
  선택한 시/군/구 안의 LH·지자체 공공임대주택(국민임대·영구임대·행복주택 등) 단지
  목록을 가져옵니다. 국토부 실거래가 API에 이미 쓰는 `lawdCd`(5자리 법정동코드)를 앞
  2자리(`brtcCode`)+뒤 3자리(`signguCode`)로 그대로 나눠 쓸 수 있어 기존 지역 데이터와
  바로 맞물립니다.
- **LH 청약센터 공지사항 목록 조회 서비스** (`lib/lhNotice.js`, data.go.kr 15058222):
  구/군 이름이 제목에 포함된 LH 공지사항(모집공고 등)을 가져옵니다. 이 API는 지역
  코드로 거르는 기능이 없고 제목/본문 키워드 검색만 지원해서, "구/군 이름이 제목에
  들어간 공지"만 잡히는 최선의 노력(best-effort)성 부가 정보입니다 — 0건이 나와도
  정상입니다.
- **청약홈 분양정보 조회 서비스(한국부동산원) — APT 오퍼레이션만** (`lib/applyhome.js`,
  data.go.kr 15098547): 진행 중이거나 최근 접수한 아파트 청약 공고(민간분양·공공분양·
  신혼희망타운 포함)를 시/도 단위로 가져옵니다. 지역으로 서버가 걸러주는 파라미터가
  없어서, 넉넉히(최대 300건) 받아온 뒤 이 파일 안에서 시/도 이름으로 직접 필터링합니다.
  청약홈 응답의 지역명이 "서울특별시"가 아니라 "서울"처럼 축약형으로 오기 때문에, 17개
  시/도 전체를 축약형으로 매핑한 표(`SIDO_SHORT_NAME`)를 두고 느슨한 부분일치까지
  안전망으로 걸어뒀습니다.

세 API 모두 응답을 감싸는 최상위 래퍼 키(예: `dsList`, `data` 등)가 활용신청 승인 전이라
문서로 완전히 확인되지 않은 경우가 있어, `lib/netFetch.js`에 새로 추가한
`extractItemArray()`가 흔히 쓰이는 후보 키들(`dsList/list/items/item/data/results/
resultList`)을 먼저 시도하고, 그래도 못 찾으면 응답 객체 안에서 배열인 값을 한 단계
더 파고들어 찾아내는 방어적인 방식으로 파싱합니다. odcloud.kr(청약홈 API가 올라간
플랫폼) 응답은 `{ data: [...] }` 형식이 이 플랫폼 전반의 공통 규격이라 신뢰도가 높지만,
혹시 다를 경우를 대비해 이 파일도 같은 방어 로직을 한 번 더 거칩니다.

### 22-2. 의도적으로 제외한 것들

- **마이홈포털 공공주택 모집공고 조회 서비스**(15108420), **마이홈포털 공공임대주택
  단지정보 조회 서비스**(15110581): 정확한 응답 필드명이 로그인 후에만 열리는 첨부파일
  안에만 있어 이번 조사로는 확인할 수 없었습니다. 짐작으로 필드를 매핑하면 값이 전부
  비거나 엉뚱하게 나올 위험이 커서 제외했습니다.
- **청약홈 분양정보 조회 서비스의 나머지 4개 오퍼레이션**(오피스텔·무순위·민간임대·
  임의공급): APT 오퍼레이션과 같은 데이터셋 안에 있지만 주택유형별로 필드 스키마가
  달라서, 문서로 확인된 APT만 우선 구현하고 나머지 4개는 제외했습니다. 필요하면 문서
  확인 후 `lib/applyhome.js`에 같은 방식으로 추가할 수 있습니다.

이 두 경우 모두 API 자체가 없다는 뜻이 아니라, **필드명을 확실히 알기 전까지는 붙이지
않는다**는 이 프로젝트의 기존 원칙을 그대로 지킨 결과입니다.

### 22-3. 화면에 보이는 위치와 동작 방식

- **① 어디로 갈지 추천받기(RankFlow)**: 순위가 매겨진 상위 10개 지역 각각의 결과
  카드 맨 아래에 "공공주택 정보" 섹션이 표시됩니다. 청약홈 분양 공고 → LH·지자체
  공공임대주택 단지 → LH 공지사항 순으로, 있는 것만 나옵니다.
- **② 지역은 정했어요(DistrictFlow)**: 지역을 선택하면(매물 검색 버튼을 누르기 전에도)
  바로 그 지역의 공공주택 정보를 보여주는 패널이 나타납니다. API 키가 하나도 없으면
  안내 문구만, 키는 있는데 그 지역에 해당 사항이 없으면 "찾지 못했습니다" 안내만
  표시됩니다.
- 세 API 모두 `MYHOME_SERVICE_KEY`/`LH_NOTICE_SERVICE_KEY`/`APPLYHOME_SERVICE_KEY`
  (`.env.example` 참고) 중 설정된 것만 채워지고, 하나도 없으면 이 섹션 전체가 조용히
  나타나지 않습니다 — 국토부 실거래가 API와 동일한 "키 없으면 폴백" 철학입니다. 실패해도
  순위·예산 계산·매물 후보 등 핵심 기능에는 전혀 영향이 없습니다.
- 응답은 30분간 메모리에 캐시됩니다(단지/공고 목록은 자주 바뀌지 않는 정보라서).

### 검증

data.go.kr 실제 서비스키는 이 샌드박스에서 발급받아 승인받을 수 없어(승인까지 보통
1~2일 소요), 세 함수 각각에 `QA_MOCK_PUBLIC_HOUSING=1` 환경변수로 동작하는 임시 목(mock)
데이터를 넣어 화면 렌더링을 검증한 뒤 코드에서 완전히 제거했습니다(제거 후
`grep -rn "QA_MOCK_PUBLIC_HOUSING" lib/ app/`로 잔여 코드가 없음을 확인). 확인한 내용:

- `/api/public-housing`이 목 데이터를 받아 지역코드별로 정상적으로 묶어 반환하는 것
- ①번 흐름(RankFlow)에서 상위 지역 카드마다 청약홈 공고/LH 단지/LH 공지 3개 그룹이
  올바른 제목과 값으로 표시되는 것 (스크린샷으로 레이아웃 확인)
- ②번 흐름(DistrictFlow)에서 지역 선택 즉시(매물 검색 전에도) 같은 정보가 표시되는 것,
  제목이 컴포넌트 자체 제목과 중복 렌더링되던 문제를 발견해 수정한 것
- API 키를 하나도 설정하지 않은 상태(포트를 분리해 별도 서버로 재확인)에서는 "공공주택
  API 키가 설정되어 있지 않습니다" 안내만 나오고 콘솔 에러 없이 다른 기능은 그대로
  동작하는 것
- `rm -rf .next node_modules && npm install && npm run build`로 처음부터 다시 빌드해
  타입/린트 오류 없이 통과하는 것

### 22-4. (수정) 같은 시/도 안 여러 구/군에서 청약홈 공고가 똑같이 중복 표시되던 문제

"① 어디로 갈지 추천받기"에서 순위 상위 10개 지역 중 같은 시/도(예: 서울특별시)에 속한
구/군이 여러 개 있으면, 모든 카드에 정확히 똑같은 청약홈 분양 공고 목록이 반복해서
나오는 문제가 있었습니다. 원인은 버그가 아니라 원본 데이터의 한계입니다 — 청약홈 API가
애초에 시/군/구가 아니라 시/도 단위로만 지역을 구분해 주기 때문에, 서울의 어느 구를
조회하든 "서울특별시 전체" 공고 목록을 그대로 돌려줍니다. 다만 화면에는 이 사실이
드러나지 않아 "같은 내용이 중복으로 보이는 버그"처럼 보였습니다.

두 가지로 고쳤습니다:

- **표시 중복 제거**: `RankFlow.js`에서 top10 중 같은 시/도가 이미 앞에서 청약홈 공고를
  보여줬다면(순위가 더 높은 카드), 그 뒤에 나오는 같은 시/도의 다른 구/군 카드에서는
  청약홈 공고 그룹을 비웁니다(가장 순위가 높은 카드 하나에만 표시). LH 공공임대 단지와
  LH 공지사항은 애초에 구/군 단위로 조회되는 데이터라 이 문제가 없어 그대로 뒀습니다.
- **제목에 범위 명시**: `PublicHousingSection.js`의 "청약홈 분양 공고" 제목 옆에
  "(OO시/도 전체)"를 붙여서, 이 목록이 그 구/군 하나만의 공고가 아니라 시/도 전체
  공고라는 걸 명확히 했습니다. "② 지역은 정했어요" 화면에서도 동일하게 표시됩니다.

Playwright로 top10 카드 10개를 모두 검사해, 서울특별시에 속한 9개 구 중 순위가 가장
높은 1개(종로구) 카드에만 청약홈 공고가 표시되고 나머지 8개에는 표시되지 않는 것,
제목에 "(서울특별시 전체)"가 정상적으로 붙는 것을 확인했습니다.

### 22-5. "공공주택 정보"를 별도 탭으로 분리(시/도 기준)

22-4번에서 같은 시/도 안 중복 표시 문제를 임시로 고쳤지만, 근본적으로는 "구/군 카드
안에 시/도 단위 정보를 끼워 넣는" 구조 자체가 어색했습니다. 청약홈 분양 공고가 원래
시/도 단위 데이터라는 걸 화면 구조에도 그대로 반영하는 게 낫겠다고 판단해, ①/② 카드
안에 있던 공공주택 정보를 전부 빼고 **"③ 공공주택 정보"라는 새 탭**으로 옮겼습니다.

- **화면**: 시/도를 고르는 드롭다운 하나만 있는 화면입니다(`PublicHousingFlow.js`).
  ①/② 화면에는 이 탭으로 안내하는 한 줄짜리 안내문만 남겼습니다.
- **청약홈 분양 공고 / LH 공지사항**: 원래도 시/도(공고)·키워드(공지) 단위라 22-1번과
  동일한 방식으로 그대로 조회합니다. LH 공지사항은 이제 구/군 이름 대신 시/도 축약형
  이름("서울특별시" -> "서울")을 키워드로 검색합니다.
- **LH 공공임대주택 단지**: 이 API는 구/군 단위로만 문서화되어 있어서, 선택한 시/도
  안의 모든 구/군을 병렬로 호출한 뒤 하나로 합쳐서 보여줍니다(`app/api/
  public-housing-sido/route.js`). 각 단지 앞에 "종로구 · 단지명"처럼 구/군 이름을
  붙여서 어느 구/군 소속인지 알 수 있게 했고, 최신 모집공고일 순으로 정렬한 뒤 상위
  60건만 보여줍니다(그보다 많으면 "전체 N건 중 최근 60건만 표시합니다" 안내가 붙습니다).
  구/군이 많은 시/도(경기도 등)는 호출 수가 늘어나지만, 구/군별 결과가 각각 30분씩
  캐시되어 있어 반복 조회 비용은 낮습니다.
- 기존 `/api/public-housing`(구/군 단위) 엔드포인트는 더 이상 쓰는 화면이 없어 삭제하고,
  `/api/public-housing-sido`(시/도 단위)로 대체했습니다.

Playwright로 확인한 내용: "③ 공공주택 정보" 탭에서 서울특별시를 고르면 25개 구 전체의
LH 임대단지가 구/군 이름과 함께 하나로 합쳐져 나오는 것, 시/도를 경기도로 바꾸면
"(경기도 전체)"로 제목이 바뀌고 이전 시/도(서울특별시) 내용이 남아있지 않는 것, ①/②
화면에는 더 이상 공공주택 정보 섹션이 나오지 않고 안내 문구만 남는 것, 콘솔 에러 없이
빌드·동작하는 것을 확인했습니다.

## 23. 매물 후보 정렬 기준을 "최근 실거래일 우선 + 가격(낮은 것 먼저)"로 되돌림

16-2번에서 "가격 낮은 순"으로 정렬 기준을 바꿨는데, 이번에 사용자가 예전 기준(최근
실거래일 우선)으로 되돌리면서 가격도 함께 반영해달라고 요청했습니다. `lib/candidates.js`의
`findCandidates()` 정렬을 2단계 기준으로 바꿨습니다.

1. **최근 실거래일(`dealYmd`) 내림차순** — 가장 최근에 거래된 매물이 먼저 나옵니다.
2. **같은 거래월이면 총액(전세/월세는 보증금 총액) 오름차순** — 동률일 때만 가격이
   낮은 매물이 먼저 나옵니다.

①모드(추천 결과 카드)·②모드(지역 선택 후 매물 찾기) 둘 다 같은 `findCandidates()`를
공유해서 쓰기 때문에, 이 한 곳만 고치면 두 화면 모두에 반영됩니다. 지도 핀도 이미
정렬된 목록의 상위 몇 건을 그대로 쓰므로 자연스럽게 같은 순서로 찍힙니다.

### 검증

실거래가 API에 의존하지 않고 정렬 로직만 검증하기 위해, `fetchRecentListings`에
`QA_MOCK_SORT_TEST=1`로 동작하는 임시 목(mock) 데이터(거래월과 가격을 일부러 서로
엇갈리게 배치: 최신월·고가 / 구월·고가 / 구월·저가 / 최구월·최저가 4건)를 넣어
`/api/district-search`와 `/api/recommend`(①·② 양쪽) 응답의 매물 순서를 직접 확인한 뒤
코드에서 완전히 제거했습니다(제거 후 `grep -rn "QA_MOCK_SORT_TEST" lib/ app/`로 잔여
코드가 없음을 확인). 결과: 최신월·고가 → 구월·저가 → 구월·고가 → 최구월·최저가 순으로
나와, "최근 거래일 우선, 동률이면 가격 낮은 순"이 정확히 의도대로 동작하는 것을
확인했습니다. `rm -rf .next && npm run build`로 다시 빌드해 오류 없이 통과하는 것도
확인했습니다.

## 24. 시/도 전체 검색 시 순위 10위 밖 지역도 "더보기"로 볼 수 있게 함

경기도처럼 지역이 42개나 되는 시/도를 "시/도로 찾기"로 검색하면, 화면에는 항상 상위
10개 지역만 카드로 보였습니다. 평택시·안성시처럼 순위가 밀리는 지역은 실제로 채점
대상에는 포함되어 있었지만(서버는 처음부터 poolDistricts 전체를 채점해서 `results`
배열 전체를 응답에 담아 보냅니다) 화면에서 `data.results.slice(0, 10)`으로 항상 앞
10개만 잘라서 보여주고 있었습니다 — 그래서 "경기도 전체를 대상으로 했는데 왜 특정
지역이 안 나오나요?"로 오해할 수 있었습니다.

기존 매물 후보 목록의 "더보기"(`CandidateList`)와 같은 패턴을 순위 목록에도 그대로
적용했습니다.

- `app/components/RankFlow.js`의 `Results` 컴포넌트에 `visibleCount` 상태를 추가해,
  처음엔 상위 10개(`RANK_INITIAL_VISIBLE`)만 보여주고 "더보기"를 누르면 10개씩
  (`RANK_PAGE_SIZE`) 더 펼칩니다. 새로 검색하면(`data`가 바뀌면) 다시 10개로 초기화됩니다.
- 이 값은 서버가 이미 계산해서 응답에 다 담아 보낸 `data.results`(전체 지역 순위)를
  그냥 더 잘라서 보여주는 것뿐이라, "더보기"를 눌러도 추가 API 호출은 없습니다(즉시
  펼쳐집니다).
- 다만 실제 매물 후보(`candidatesByDistrict`)는 여전히 상위 10개 지역만 조회합니다
  (`app/api/recommend/route.js`의 `CANDIDATE_DISTRICT_COUNT`, README 16-1·18번 참고 —
  전국 단위로 조회 대상을 늘리면 실거래가 API 호출이 지역 수만큼 늘어나기 때문입니다).
  그래서 순위 10위 밖 지역의 카드는 매물 후보 없이 순위·예상 시세만 나오고, 기존에
  이미 있던 "상위 N개 지역만 매물을 조회합니다(미조회, 데이터 없음 아님)" 안내 문구가
  자연스럽게 그 카드에도 표시됩니다.

### 검증

Playwright로 "시/도로 찾기" → 경기도로 검색해 확인했습니다: 처음엔 카드 10개만
보이고 평택·안성 둘 다 화면에 없는 것, "지역 10개 더보기(남은 32개 — 순위 11위부터)"
버튼이 정확한 남은 개수를 보여주는 것, 버튼을 4번 눌러 전체 42개 지역이 다 펼쳐지고
그 안에 평택·안성이 포함되는 것, 다 펼친 뒤에는 버튼이 사라지는 것을 확인했습니다.
기존 회귀 테스트(①/②/③ 탭 콘솔 에러 없음, 매물 정렬, 공공주택 탭)도 다시 통과하는 것을
확인했습니다.

## 25. 매물 후보 조회를 순위 상관없이 검색 대상 지역 전체로 확대(임의로 자르지 않음)

24번에서 화면에 보이는 카드 개수(순위 목록)는 "더보기"로 전체를 볼 수 있게 했지만,
실제 매물 후보 조회(국토부 실거래가 API 호출)는 여전히 상위 10개 지역으로 제한되어
있었습니다. 사용자가 "실제 매물 후보 조회도 전체를 대상으로 해줘, 알아서 자르지
말라"고 명확히 요청해서, 이 제한을 완전히 없앴습니다.

- `app/api/recommend/route.js`에서 `CANDIDATE_DISTRICT_COUNT`(=10) 상수와
  `results.slice(0, CANDIDATE_DISTRICT_COUNT)`를 없애고, 검색 대상 지역
  전체(`results` 배열 전부, 즉 반경/시/도로 좁힌 poolDistricts 전체)에 대해
  `findCandidates()`를 호출하도록 바꿨습니다. 이미 있던 지역별 개별 try/catch
  안전망(한 지역 조회가 실패해도 다른 지역·전체 응답에 영향 없음)은 그대로 유지됩니다.
- `app/components/RankFlow.js`의 `ResultCard`에서 "순위가 상위 N개 안에 안 들어서
  미조회"라는 조건부 안내 문구와 관련 로직(`candidateDistrictCount`,
  `liveEnabled` 분기, `rank` 프롭)을 전부 제거했습니다 — 이제 모든 지역이 조회되므로
  이 구분 자체가 필요 없어졌습니다. `candidates`가 있으면(0건이든 여러 건이든)
  `CandidateList`가 그대로 보여주고(0건이면 자동으로 "조건에 맞는 최근 거래를 찾지
  못했습니다" 안내), `candidates`가 아예 없는 유일한 경우는 API 키 미설정뿐이며 그건
  상단 배지로 이미 안내됩니다.
- **주의**: 지역이 매우 많은 검색(예: 반경을 넓게 잡거나 지역이 많은 시/도)은 그만큼
  국토부 실거래가 API 호출도 함께 늘어나 응답이 느려지거나(지역 수 × 조회 개월 수만큼
  동시 요청) 드물게 429(요청 과다) 오류가 날 수 있습니다. 이미 있던 지역별 안전망
  덕분에 그런 경우에도 일부 지역만 실패하고 나머지는 정상적으로 채워집니다(§13-1의
  일부 지역 조회 실패 안내 배너가 그대로 처리).

### 검증

실제 서비스키 없이 로직만 검증하기 위해, `fetchRecentListings`와
`fetchAvgPricePerPyeong`(둘 다 lib/molit.js)에 `QA_MOCK_ALL_DISTRICTS=1`로 동작하는
임시 목(mock) 데이터를 넣어 경기도(42개 지역) 전체 검색 결과를 확인한 뒤 코드에서
완전히 제거했습니다(제거 후 `grep -rn "QA_MOCK_ALL_DISTRICTS" lib/ app/`로 잔여 코드가
없음을 확인). `/api/recommend` 응답을 직접 확인해 `results`(42개)와
`candidatesByDistrict`(42개) 개수가 정확히 일치하고, 평택시·안성시를 포함한 모든
지역에 후보가 채워지는 것을 확인했습니다. Playwright로는 "더보기"를 4번 눌러 42개
카드를 전부 펼친 뒤 평택시·안성시 카드에 실제 매물 후보(목 데이터)가 표시되고
"미조회" 같은 예전 안내 문구는 더 이상 나오지 않는 것, 콘솔 에러가 없는 것을
확인했습니다. `rm -rf .next node_modules && npm install && npm run build`로 처음부터
다시 빌드해 오류 없이 통과하는 것도 확인했습니다.

## 26. 시/도 전체 검색 결과에서 구/군별 매물 후보 타이틀을 굵게+색깔로 구분

25번으로 매물 후보 조회가 검색 대상 지역 전체로 늘어나면서, 경기도처럼 지역이 많은

됩니다. 지금 보고 있는 목록이 어느 구/군 것인지 한눈에 구분하기 어렵다는 피드백을

## 27. 같은 단지가 층/거래월만 다른 채 여러 건 보일 때 구분 뱃지 추가

사용자가 올려준 화면에서 "지제역더샵센트럴시티"가 가격만 다른 채(7.3억/8.4억/9.2억/
9.5억원) 4건 나란히 보였는데, 나머지 정보(동, 평형, 준공연도)가 똑같아 보여 "중복
아닌가?"라는 문의가 있었습니다.

먼저 실제로 중복 데이터인지부터 확인했습니다. `lib/candidates.js`의
`dedupeLatest()`는 이미 "단지명 + 반올림한 전용면적 + 층"이 모두 같을 때만 최신
거래로 합칩니다(주석 참고 — 예전엔 층을 기준에 넣지 않아서 서로 다른 매물이
1건으로 뭉개지는 문제가 있었고, 그걸 고친 이후로 층까지 같아야 진짜 중복으로
취급합니다). 즉 화면에 4건이 남아있다는 건 이 4건이 서로 층 또는 거래월이 달라서
실제로는 다른 매물(다른 시점에 팔린 다른 호실)이라는 뜻이지, 데이터가 중복으로
잘못 들어온 게 아닙니다 — 실제로 QA로 재현해 본 4건도 층(4/7/12/19층)과
거래월(2026.06~08)이 전부 달랐습니다. 그래서 삭제가 아니라 "다른 부분을 표시나게
해달라"는 사용자의 두 번째 제안대로, 구분 정보를 더 눈에 띄게 만드는 방향으로
고쳤습니다.

- `app/components/RankFlow.js`의 `CandidateList`와 `app/components/DistrictFlow.js`의
  `DistrictCandidateItem` 양쪽에 동일하게, 가격 바로 아래에 층/거래월을 강조하는
  뱃지 줄(`.candidate-distinguish` 안에 `.candidate-chip` 두 개: "19층", "거래
  2026.08")을 추가했습니다. 기존에는 이 두 값이 아래쪽 회색 메타 줄에 다른 정보(동,
  평형, 준공연도)와 섞여 작은 글씨로만 있어서 눈에 잘 안 띄었습니다.
  `.candidate-chip`은 `.badge.budget-ok/over`와 같은 톤(테두리+글자색, 배경 없음)의
  알약 모양이며, 지역 타이틀에 쓴 파란색(`--series-price`)과 겹치지 않도록
  주황색(`--series-commute`)을 썼습니다 — "파란색 = 어느 구/군인지", "주황색 = 이
  매물이 다른 매물과 어떻게 다른지"로 색 역할을 나눴습니다.
  중복으로 보여주던 층/거래월을 아래 메타 줄에서는 뺐습니다(같은 정보를 두 번 다른
  자리에 보여주지 않도록).
- 진짜 완전 중복(단지명+면적+층까지 같은 경우)은 여전히 `dedupeLatest()`가 최신
  거래 1건으로 합쳐서 보여주므로, 이번 변경과 무관하게 그대로 유지됩니다.

## 28. 실제 매물이 있는 지역 카드 강조 + 지도 마커 클릭 시 카드 포커싱

25번 이후로 검색 대상 지역 전체가 카드로 나오면서(예: 반경 15km 안 28개 지역), 실제
매물 후보가 있는 카드와 0건인 카드가 섞여 목록이 길어졌습니다. 사용자가 캡처한
화면에서 지도 위 회색 매물 핀(예산 이내/초과가 정해지지 않은 매물 후보 —
`mapColors.js`의 `budgetFitColor`가 반환하는 회색)이 몇 개 안 되는데, 그게 목록의
어느 카드(예: "서울특별시 중구", "마포구")에 해당하는지 목록만 봐서는 구분이 안
된다는 피드백을 받았습니다. 또, 지도 마커를 클릭하면 원래도 해당 카드로
스크롤은 됐지만(`handleMarkerClick`), 스크롤된 카드 자체에 아무 강조 표시가 없어
"포커싱"됐다는 느낌이 없었습니다.

- `app/components/RankFlow.js`의 `ResultCard`에서 `candidates && candidates.length > 0`인
  카드에는 `has-candidates` 클래스를 붙여 초록 테두리로 강조하고, 카드 제목 옆에
  "실제 매물 N건" 배지(기존 `.badge.budget-ok` 스타일 재사용)를 추가했습니다. 이제
  목록을 쭉 훑어보기만 해도 실제 매물이 있는 지역이 바로 눈에 띕니다.
- `Results` 컴포넌트가 이미 갖고 있던 `selectedDistrict`(지도 마커 클릭 시
  `handleMarkerClick`이 갱신하는 상태)를 `ResultCard`에 `isSelected` 프롭으로
  내려보내, 마커를 클릭해서 스크롤된 카드에는 `selected` 클래스(파란 테두리 +
  바깥 그림자)를 붙였습니다. `app/globals.css`에 `.result-card.has-candidates`(초록
  테두리)와 `.result-card.selected`(파란 테두리+그림자) 스타일을 추가했는데, 그림자는
  테두리 바깥쪽에 덧붙는 방식이라 두 스타일이 동시에 적용돼도(매물이 있는 지역을
  마커 클릭으로 골랐을 때) 서로 가리지 않습니다.
- "지역으로 찾기"(DistrictFlow, ②번 모드)는 지역을 하나만 검색해 카드가 하나뿐이라
  이런 구분이 필요 없어 건드리지 않았습니다.

### 검증

`lib/molit.js`의 `fetchRecentListings`/`fetchAvgPricePerPyeong`에
`QA_MOCK_HIGHLIGHT_TEST=1`로 동작하는 임시 목을 넣어, 서울 중구(11140)·마포구(11440)
에만 실제 매물이 있는 것처럼(그 외 지역은 0건) 재현한 뒤 코드에서 완전히
제거했습니다(제거 후 `grep -rn "QA_MOCK_HIGHLIGHT_TEST" lib/ app/`로 잔여 코드가
없음을 확인). Playwright로 반경 검색(서울시청 부근 15km) 결과 28개 카드 중 중구·

확인했고, 스크린샷으로 초록 테두리를 눈으로 확인했습니다. 이어서 지도 위 마커를
순서대로 클릭해 종로구 마커를 클릭했을 때 종로구 카드에 `selected` 클래스(파란
테두리+그림자)가 붙고 그 카드가 화면에 스크롤되는 것을 확인했습니다. `rm -rf .next
node_modules && npm install && npm run build`로 처음부터 다시 빌드해 오류 없이
통과하는 것, API 키 미설정 시에도 정상 동작하는 것을 확인했습니다.

## 29. 조건 입력을 단계별 슬라이드로 분리(모바일 최적화)

①·②모드 모두 조건 입력 필드(위치/지역, 거래유형·평형·예산, 중요도 등)가 한 화면에
쭉 이어져 있어서, 특히 휴대폰에서는 스크롤이 매우 길었습니다. 사용자가 "조건을
슬라이드로 바꿔줘, 휴대폰에서도 최적화되게 해줘"라고 요청해서, 두 모드 모두 입력
폼을 단계별 슬라이드(한 번에 한 단계만 보여주고 "다음/이전" 버튼으로 넘기는 방식)로
바꿨습니다.

- 새 공용 컴포넌트 `app/components/WizardProgress.js`: 상단에 진행 표시줄(번호
  동그라미 + 연결선)을 보여줍니다. 완료한 단계는 초록 체크, 현재 단계는 검게 채워진
  동그라미, 남은 단계는 회색 테두리만. 휴대폰처럼 좁은 화면(480px 이하)에서는 글자
  라벨("위치","조건" 등)을 숨기고 번호+선만 남겨 한 줄에 다 들어오게 했습니다.
- **①모드(`RankFlow.js`)**: 기존 "1. 어디서부터 찾아볼까요?"(위치·지도) / "2. 원하는
  집 조건"(거래유형·주택유형·준공연식·방/화장실·예산·평형) / "3. 무엇을 가장
  중요하게 볼까요?"(가중치) 3개 섹션을 그대로 3단계 슬라이드로 나눴습니다. `step`
  상태(1~3)로 현재 단계만 렌더링하고, 예전에 있던 "상세 조건 접기/펼치기" 토글
  (`conditionsOpen` 상태, `.conditions-toggle`/`.conditions-slide` 클래스)은 이제
  단계 구분 자체가 그 역할을 대신하므로 완전히 제거했습니다. 검색 실행 버튼("이사 갈
  곳 추천받기")은 마지막 단계(3단계)에서만 나타납니다.
- **②모드(`DistrictFlow.js`)**: "1. 지역 선택"(시/군/구·거래유형·주택유형·평형) /
  "2. 필요 예산(자동 계산)"(예산 자동계산 결과 + 예산/준공연식/방/화장실 조정) 2단계로
  나눴습니다. 예산 자동계산(`estimate`)은 지역을 고르면 곧바로 조회가 시작되는데,
  아직 응답이 안 왔을 때 2단계로 넘어가면 화면이 비어 보일 수 있어 "예산을 계산하고
  있어요..." 안내를 추가했습니다.
- 단계가 바뀔 때마다(`key={step}`) 컴포넌트를 새로 마운트해 살짝 옆에서 미끄러져
  들어오는 애니메이션(`.wizard-step`, `wizard-step-in` 키프레임)을 주어 "슬라이드"
  느낌을 살렸고, `prefers-reduced-motion` 설정 시에는 애니메이션을 끕니다. 폼 위쪽에
  `ref`를 달아 단계를 넘길 때마다 폼 맨 위로 부드럽게 스크롤(`scrollIntoView`)해서,
  긴 단계에서 짧은 단계로 이동해도 화면 중간 어색한 위치에 남지 않게 했습니다.
  ①모드에서 위치 선택 지도는 1단계에서만 마운트되므로(다른 단계로 넘어가면 언마운트),
  지도 인스턴스를 여러 개 동시에 띄워두지 않아 성능에도 도움이 됩니다.
- 이전/다음 버튼(`.wizard-btn-prev`/`.wizard-btn-next`)과 마지막 단계의 제출 버튼은
  `.wizard-nav` 안에서 나란히 절반씩 폭을 차지하도록 했고(`flex:1`), 휴대폰에서는
  버튼 패딩과 글씨를 살짝 키워 터치하기 쉽게 했습니다.

### 검증

Playwright로 휴대폰 화면 크기(390×844)에서 ①모드 1→2→3단계를 "다음" 버튼으로
전부 넘겨보고 각 단계 내용이 올바르게 바뀌는 것, 3단계에서 실제 제출 버튼이
나타나 클릭 시 검색이 정상 실행되는 것, "이전"으로 되돌아가는 것을 확인했습니다.
데스크톱 폭(1000px)에서는 진행 표시줄에 "위치·조건·중요도" 글자 라벨이 정상적으로
보이는 것을 스크린샷으로 확인했습니다. ②모드도 같은 방식으로 1→2단계 이동 시
자동계산된 예산 범위가 정상적으로 표시되는 것을 확인했습니다. `rm -rf .next
node_modules && npm install && npm run build`로 처음부터 다시 빌드해 오류 없이
통과하는 것, API 키 미설정 시에도 정상 동작하는 것을 확인했습니다.

## 30. 단계별 슬라이드(마법사) → 오른쪽에서 나타나는 슬라이드 패널로 변경

29번에서 만든 "다음/이전" 버튼 단계별 마법사에 대해, 사용자가 다른 서비스(지도가
항상 보이고 "조건" 버튼을 누르면 조건 입력이 화면 오른쪽에서 슬라이드로 나타나는
필터 패널)의 화면 예시를 보여주며 "버튼 말고, 오른쪽에서 나왔다 들어갔다하게
슬라이드로 바꿔줘"라고 명확히 피드백을 주었습니다. 예시 화면은 어디까지나 상호작용
방식(버튼 클릭 → 오른쪽에서 슬라이드 패널 등장)의 참고였을 뿐, 그 사이트의 필터
항목을 그대로 옮긴 것은 아닙니다. 이 요청에 따라 29번의 "다음/이전" 버튼 마법사를
걷어내고, 지도처럼 항상 봐야 하는 핵심 내용은 메인 화면에 그대로 두고 나머지
조건은 버튼을 눌러야 오른쪽에서 슬라이드로 나타나는 패널 안에 넣는 방식으로
다시 만들었습니다.

- 새 공용 컴포넌트 `app/components/SlideDrawer.js`: `open`/`onClose`/`title`/
  `children` props를 받는 오른쪽 슬라이드 패널입니다. 배경을 어둡게 덮는
  `.drawer-backdrop`과 패널 본체 `.drawer-panel`을 열려 있지 않을 때도 항상
  DOM에 렌더링해 두고 CSS `transform`(패널)/`opacity`(배경)만 토글하는 방식으로
  구현했습니다 — 조건부로 마운트/언마운트했다면 "닫힐 때 오른쪽으로 사라지는"
  애니메이션 자체가 재생되지 않기 때문입니다. 패널 안의 입력값들은 이 컴포넌트가
  아니라 부모(`RankFlow`/`DistrictFlow`)의 state에 있으므로, 패널을 열고 닫아도
  값은 그대로 유지됩니다. 열려 있는 동안은 `document.body.style.overflow =
  "hidden"`으로 뒤 배경 스크롤을 막고, `Escape` 키로도 닫을 수 있게 했습니다(29번의
  `WizardProgress.js`는 더 이상 쓰지 않아 삭제했습니다).
- **①모드(`RankFlow.js`)**: "1. 어디서부터 찾아볼까요?"(위치·지도) 섹션은 메인
  화면에 항상 보이고, 그 아래 "원하는 집 조건 · 중요도 설정" 버튼을 누르면 예전
  2·3단계였던 "원하는 집 조건"(거래유형·주택유형·준공연식·방/화장실·예산·평형)과
  "무엇을 가장 중요하게 볼까요?"(가중치)가 오른쪽 패널 안에 함께 나타납니다.
  버튼 아래에는 현재 설정된 예산/평형 범위를 한 줄 요약으로 미리 보여줘서, 패널을
  열지 않고도 지금 어떤 조건인지 알 수 있게 했습니다. 검색 실행 버튼("이사 갈 곳
  추천받기")은 패널 밖 메인 화면에 항상 있어 패널을 열지 않고도 바로 누를 수
  있습니다.
- **②모드(`DistrictFlow.js`)**: "1. 지역 선택"(시/군/구·거래유형·주택유형·평형)은
  메인 화면에 항상 보이고, "필요 예산 · 세부 조건 설정" 버튼을 누르면 "2. 필요
  예산(자동 계산)" 내용(예산 자동계산 결과 + 예산/준공연식/방/화장실 조정)이
  오른쪽 패널에 나타납니다. 마찬가지로 버튼 아래에 계산된 예산 범위를 미리
  보여줍니다. 매물 검색 버튼도 패널 밖 메인 화면에 항상 있습니다.
- 휴대폰처럼 좁은 화면(480px 이하)에서는 패널이 `min(420px, 92vw)` 대신 화면
  전체 폭(`100vw`)을 차지하도록 했습니다 — 이 경우 배경(backdrop)을 탭해서 닫는
  여백이 거의 남지 않으므로, 패널 우측 상단의 ✕ 버튼이나 `Escape`로 닫는 것이
  주된 방법입니다.

### 검증

Playwright로 데스크톱(1280×900)·휴대폰(390×844) 두 화면 크기에서, 두 모드 모두
"조건 설정" 버튼을 눌러 패널이 오른쪽에서 슬라이드로 나타나는 것, 패널 안에서
값을 바꾼 뒤 ✕ 버튼으로 닫고 다시 열었을 때 값이 그대로 유지되는 것(부모 state에
있으므로), `Escape` 키로 닫히는 것, 데스크톱 폭에서는 배경(backdrop)을 클릭해도
닫히는 것을 확인했습니다. 패널이 열려 있는 동안은 배경 전체가 딤 처리되어 뒤
화면(모드 전환 탭 포함) 클릭이 막히는 것도 의도한 동작으로 확인했습니다(모달
방식 패널이므로 먼저 패널을 닫아야 다른 조작이 가능합니다). 두 모드 모두 패널
밖 메인 화면에서 제출 버튼이 항상 보이고 정상적으로 검색이 실행되는 것도
확인했습니다. `rm -rf .next node_modules && npm install && npm run build`로
처음부터 다시 빌드해 오류 없이 통과하는 것, API 키 미설정 시에도 `/api/recommend`가
정상적으로 참고값 모드로 동작하는 것을 확인했습니다.

## 31. Cloudflare Workers 배포 지원 추가

웹 배포처를 Vercel 대신 Cloudflare(Workers)로 바꿔달라는 요청에 따라, 이 프로젝트를
Cloudflare에 올릴 수 있도록 설정을 추가했습니다. Cloudflare는 최근 Next.js를
Cloudflare Workers에 올리는 방법으로 새 도구인 "vinext"를 기본으로 안내하고
있지만, 이 프로젝트처럼 이미 완성된 표준 Next.js 앱(스트리밍 API 응답, 커스텀
fetch 등)에는 훨씬 오래 검증된 **OpenNext Cloudflare 어댑터**
(`@opennextjs/cloudflare`)가 더 안전하다고 판단해 그쪽을 사용했습니다. Next.js
버전(14.2.35)과 정확히 호환되는 `@opennextjs/cloudflare@1.15.1` + `wrangler@^4.59.2`
조합을 선택했습니다(최신 버전은 Next 15 이상을 요구해서 이 프로젝트에는 설치할 수
없었습니다).

### 추가/변경된 파일

- `wrangler.jsonc`(신규): Cloudflare Workers 배포 설정. 워커 이름(`moving-advisor`),
  진입점(`.open-next/worker.js`), Node.js 호환 플래그(`nodejs_compat`), 정적 파일
  서빙(`assets`) 등을 지정합니다.
- `open-next.config.ts`(신규): OpenNext 빌드 설정. 이 프로젝트는 ISR/정적 재생성을
  쓰지 않아 기본값 그대로(`defineCloudflareConfig()`)면 충분합니다.
- `next.config.mjs`: `next dev`로 로컬 개발할 때도 Cloudflare 바인딩에 접근할 수
  있게 해주는 `initOpenNextCloudflareForDev()`를 추가했습니다(try/catch로 감싸서
  패키지가 없어도 개발 서버 자체는 깨지지 않게 했습니다).
- `public/_headers`(신규): 빌드마다 파일명에 해시가 붙는 `/_next/static/*` 정적
  파일을 1년 장기 캐시하도록 지정합니다.
- `package.json`: `cf:preview`(로컬에서 실제 Workers 런타임으로 미리보기),
  `cf:deploy`(빌드+배포), `cf:typegen` 스크립트를 추가했습니다. 기존
  `dev`/`build`/`start`는 그대로 남아 있어 Vercel이나 일반 Node 호스팅에도 여전히
  쓸 수 있습니다.
- `.gitignore`: OpenNext/Wrangler가 매 빌드마다 새로 만드는 `.open-next/`,
  `.wrangler/`, `cloudflare-env.d.ts`, `.dev.vars`를 제외했습니다.

### `undici` 지연 로딩으로 변경 (Cloudflare 배포 시 중요한 버그 수정)

`lib/molit.js`와 `lib/netFetch.js`는 회사·기관 네트워크의 TLS 검사를 우회하는
선택 기능(`MOLIT_ALLOW_INSECURE_TLS=1`, README 13-2번)을 위해 `undici` 패키지를
맨 위에서 정적으로 `import`하고 있었습니다. 이 상태로 Cloudflare Workers에
올려보니(로컬에서 `npx wrangler dev`로 실제 Workers 런타임 위에서 테스트),
그 기능을 켜지 않았는데도(API 키 미설정 상태에서도) `/api/recommend` 같은
API 라우트가 전부 `ReferenceError: WeakRef is not defined`로 500 에러가
났습니다 — `undici` 모듈이 로드되는 것만으로 내부적으로 `WeakRef`(Workers
런타임에 없는 전역 객체)를 참조하기 때문이었습니다. 이 기능은 애초에 로컬
PC/회사망의 TLS 검사를 우회하기 위한 것이라 Cloudflare 서버에서는 필요하지도
않으므로, `import("undici")`로 **그 기능이 실제로 켜졌을 때만** 지연 로딩하도록
두 파일을 고쳤습니다 — 평소(대부분의 경우)에는 `undici`가 아예 로드되지 않아
Cloudflare Workers에서도 문제없이 동작하고, 로컬 회사망 우회 기능 자체는 이전과
동일하게 그대로 씁니다.

### 배포 방법 (사용자가 직접 실행해야 하는 단계)

Vercel 때와 마찬가지로, 이 샌드박스는 보안 정책상 Cloudflare API에 직접
접속(로그인·배포)할 수 없습니다 — `npx wrangler dev`로 로컬 미리보기까지는
확인했지만, 실제 `wrangler deploy`는 사용자의 Cloudflare 계정 인증이 필요해
사용자의 컴퓨터에서 직접 실행해야 합니다.

1. (최초 1회) [Cloudflare 계정](https://dash.cloudflare.com/sign-up)을 만듭니다(무료).
2. 프로젝트 폴더에서 `npm install` 실행(이미 `wrangler`, `@opennextjs/cloudflare`가
   `package.json`에 포함돼 있어 자동으로 설치됩니다).
3. `npx wrangler login` 실행 — 브라우저가 열리면 Cloudflare 계정으로 로그인하고
   권한을 승인합니다.
4. API 키를 쓰고 있다면(README 4·22번), Cloudflare 대시보드의 Workers & Pages >
   해당 워커 > Settings > Variables and Secrets에서 `MOLIT_SERVICE_KEY` 등을
   추가하거나, 터미널에서 `npx wrangler secret put MOLIT_SERVICE_KEY`로 등록합니다
   (`.env.local`은 로컬 전용이라 배포된 워커에는 자동으로 전달되지 않습니다).
5. `npm run cf:deploy` 실행 — 이 명령이 `next build`→OpenNext 변환→
   `wrangler deploy`를 순서대로 해줍니다. 완료되면 터미널에 실제 배포 주소
   (`https://moving-advisor.<계정서브도메인>.workers.dev`)가 출력됩니다.
6. 이후 코드를 고칠 때마다 `npm run cf:deploy`만 다시 실행하면 재배포됩니다.
   커스텀 도메인을 연결하고 싶으면 Cloudflare 대시보드의 해당 워커 > Settings >
   Domains & Routes에서 추가할 수 있습니다.

### 문제 해결: `npx wrangler login`/`cf:deploy`가 회사망·VPN에서 "fetch failed"로 실패하는 경우

`wrangler`가 직접 다음과 같이 알려주는 경우입니다:

> Wrangler detected that a corporate proxy or VPN might be enabled on your
> machine, resulting in API calls failing due to a certificate mismatch.

이건 이 프로젝트의 국토부 API 호출이 회사망에서 실패하던 것(README 13-1·13-2번)과
**원인이 완전히 같습니다** — 회사·기관 네트워크나 보안 소프트웨어가 HTTPS
트래픽을 가로채 자체 서명 인증서로 다시 서명하는 "TLS 검사"를 하는데, Node
(wrangler도 Node로 동작합니다)는 이 자체 서명 인증서를 기본적으로 신뢰하지
않기 때문입니다. Windows의 인증서 저장소(다른 프로그램·브라우저가 쓰는 곳)에는
이미 그 인증서가 등록돼 있어도, Node는 그걸 자동으로 같이 쓰지 않고 별도로
알려줘야 합니다.

**해결 방법 (권장) — 회사 루트 인증서를 Node에 알려주기:**

1. Windows 검색에서 `certmgr.msc`(현재 사용자용) 실행 → 왼쪽에서 **신뢰할 수 있는
   루트 인증 기관 > 인증서**로 이동합니다.
2. 목록에서 일반적인 공인 인증기관(DigiCert, Let's Encrypt 등)이 아니라 회사
   이름이나 보안 제품 이름(예: Zscaler, Netskope, Forcepoint, Palo Alto, Cisco
   Umbrella, Fortinet 등)이 붙은 인증서를 찾습니다 — 이미 README 13-1번에서
   국토부 API 문제로 이 인증서를 찾아 내보낸 적이 있다면 그 파일을 그대로
   재사용하면 됩니다.
3. 그 인증서를 오른쪽 클릭 → **모든 작업 > 내보내기** → "Base-64 로 인코딩된
   X.509(.CER)" 형식으로 선택해 예를 들어 `C:\certs\corp-root.cer`로 저장합니다.
4. 아래처럼 `NODE_EXTRA_CA_CERTS`를 설정한 뒤 같은 터미널 창에서 다시
   `npx wrangler login`(또는 `npm run cf:deploy`)을 실행합니다.

   명령 프롬프트(cmd)인 경우:
   ```
   set NODE_EXTRA_CA_CERTS=C:\certs\corp-root.cer
   npx wrangler login
   ```
   PowerShell인 경우:
   ```
   $env:NODE_EXTRA_CA_CERTS = "C:\certs\corp-root.cer"
   npx wrangler login
   ```
   매번 새로 설정하기 번거로우면 "시스템 환경 변수 편집"에서 `NODE_EXTRA_CA_CERTS`를
   영구적으로 추가해 두고 터미널을 새로 열면 계속 적용됩니다.

**그래도 안 되거나 회사 인증서를 구하기 어려운 경우 (임시 우회, 신뢰할 수 있는 회사망에서만):**

```
set NODE_TLS_REJECT_UNAUTHORIZED=0
npx wrangler login
```
이 방법은 그 터미널에서 실행하는 Node 프로세스의 인증서 검증 자체를 전부
꺼버리는 것이라(README의 `MOLIT_ALLOW_INSECURE_TLS`와 같은 종류의 절충입니다),
공용 와이파이 등 신뢰할 수 없는 네트워크에서는 쓰지 말고, 로그인/배포가 끝나면
그 환경변수를 다시 지우는 것을 권장합니다.

### 검증

Cloudflare 계정 인증이 필요한 실제 `wrangler deploy`는 이 샌드박스에서 실행할 수
없었지만, 그 앞 단계까지는 전부 실제로 실행해 확인했습니다: `npx
opennextjs-cloudflare build`로 OpenNext 번들(`.open-next/worker.js`)을 만드는
것, `npx wrangler dev --local`로 그 번들을 실제 workerd(Cloudflare Workers와
동일한 런타임) 위에서 띄우는 것, 그 위에서 홈페이지·`/api/recommend`·
`/api/subway`·`/api/district-search`(예산 자동계산)·`/api/candidate-coords`
(NDJSON 스트리밍 응답) 전부 정상 응답하는 것을 curl로 확인했습니다. Playwright로
그 Workers 런타임 위에서 실제 화면을 열어 조건 패널(30번)이 정상 동작하고
"이사 갈 곳 추천받기"를 눌러 결과 목록·지도가 정상적으로 렌더링되는 것까지
스크린샷으로 확인했습니다. 이 과정에서 `undici` 관련 버그(위 항목)를 실제로
발견하고 고쳤습니다. 고친 뒤 기존 `npm run build`/`npm run start`(Vercel·일반
Node 호스팅 경로)도 여전히 API 키 미설정 상태에서 정상 동작하는 것을 다시
확인해 회귀가 없음을 검증했습니다.
